# 提案 25 — 满速 84M 流式验证：网络带宽与端到端解码完整性

> 日期：2026-07-04
> 状态：**已实测达成**
> 关联：proposal 22（MMCM 采样）、HANDOFF §7（满速卡点）、PLAN_STAGE4（端到端数据通路）

---

## 一句话结论

**STM32F429 满血 168MHz HCLK（TRACECLK=84MHz）、4-bit 并口 ETM trace，经 FPGA MMCM 流式采样 → 千兆 UDP → PC → orbetto，端到端解出 13/15 ground-truth 调用栈。网络出口 83.6 MB/s、0 丢包。**

之前 HANDOFF §7.1 记录的"84M 网络完全不通"问题确认为**劣质网线**导致的 PHY RX CRC 错误，更换网线后消失。满速无架构障碍。

## 实测数据

### 带宽分层测试

| TRACECLK | 位宽 | 理论速率 | 实测吞吐 | 丢包率 | 判定 |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 21 MHz | 4-bit | 21 MB/s | 20.59 MB/s | 0% | ✅ 完美 |
| 42 MHz | 4-bit | 42 MB/s | 43-46 MB/s | 0% | ✅ 完美 |
| 84 MHz | 4-bit | 84 MB/s | 80.5-83.7 MB/s | 0-0.066% | ✅ 可用 |

> 84M 的微量丢包（0.066%）来自 host 端 UDP socket 缓冲溢出，加大 `rmem_max` 到 64MB 后大幅改善。FPGA 侧 FIFO 无溢出（`lost_cnt=0`）。

### 2-bit 满速结论

2-bit 满速 = 84M TRACECLK × 2 lane × DDR = **42 MB/s**，等价于 42M 4-bit（已实测 0 丢包通过）。**网络带宽对 2-bit 满速完全有保障。**

## 技术改动（本次验证过程中实施）

### 1. fpga_core_net: self-TX ARP 死锁修复

**问题**：verilog-ethernet 的 self-TX FSM 在 ARP 缓存冷（目标 MAC 未知）时死锁——FSM 持有 `tx_udp_hdr_valid` 等 IP 层 ARP resolve，而 ARP request 帧需要走同一条 TX MAC 出口，被 FSM 占住的 header valid 阻塞。

**修复**：
- `ST_HDR` 加 8ms 超时 (`hdr_timeout`)：如果 `tx_udp_hdr_ready` 在 8ms 内不拉高，退出到 `ST_BACKOFF`
- `ST_BACKOFF` 冷却 500ms 再回 `ST_IDLE` 重试：避免快速循环产生 ARP 广播风暴
- `self_busy` 定义改为仅 `ST_HDR || ST_SEND`：backoff 期间 echo/ARP reply 路径不被阻塞

### 2. trace_mmcm_stream_top: 心跳包

**问题**：无 trace 数据时 FIFO 永远为空，packetiser 永不启动，self-TX FSM 不发包——ARP 缓存过期后网络连接丢失，host 无法判断 FPGA 是否存活。

**修复**：心跳定时器（~1 秒），当 FIFO 深度不足一包且定时到时，发一个全 0x00 payload 的 1024 字节 "心跳包"（seq 正常递增）。host 端通过 payload 全零识别心跳 vs 真实 trace 数据。有 trace 数据时心跳自动抑制。

### 3. led_status.v: 双 LED 状态指示器

两颗板载 LED（active-low）用优先级编码四状态闪灯：

- **LED1 (M18) — 网络**：灭(MMCM 没锁) / 慢闪(idle) / 快闪(RX 活跃) / 常亮(持续 TX 流)
- **LED2 (N18) — Trace**：灭(采样 MMCM 没锁) / 慢闪(就绪) / 快闪(正常流式) / 常亮(FIFO 溢出报警)

### 4. BANDWIDTH_TEST 编译开关

`trace_mmcm_stream_top` 新增 `BANDWIDTH_TEST` 参数。为 1 时绕过 trace 前端和 FIFO/packetiser，直接把 clk125 字节计数器接到 fpga_core_net 的 stream 接口——纯测网络出口带宽上限（实测因 ARP 死锁问题未成功，但广播模式验证了 TX 硬件能跑满）。

## 踩坑记录

### 网线导致的 PHY RX CRC 错误（间歇性）

- **现象**：net_test LED1(M18) 快闪 = 只收到 CRC-bad 帧；FPGA 无法回 ARP，网络完全不通
- **根因**：劣质/老化网线在千兆速率下信号完整性不够，PHY 自协商到千兆但数据通道 CRC 全错
- **解法**：更换网线后一切正常
- **教训**：千兆 RGMII 对网线质量敏感，Cat5e 短线或 Cat6 为佳；调试时先用 net_test LED 确认 RX CRC 状态

### ARP 冷启动与 self-TX 的交互

FPGA 上电后第一个心跳/trace 包触发 self-TX FSM → ARP 查目标 MAC → 如果此时 host 还没发过帧到 FPGA（缓存空）→ ARP request 出去但 reply 回来之前 FSM 又占住了 TX path → 原始死锁。

**实际操作流程**（workaround）：烧完 FPGA 后从 host 发一个 UDP 到 :5002（触发 ARP 交互 + FPGA 学到 host MAC），之后 self-TX 的 ARP 查询直接命中缓存不死锁。backoff 机制保证即使第一次失败，500ms 后重试时缓存已暖。

## 与产品目标（2-bit 满速）的关系

| 层 | 4-bit 满速已验证 | 2-bit 满速预期 |
|----|:---:|:---:|
| 网络出口 | 84 MB/s ✅ | 42 MB/s（远低于出口能力）✅ |
| 采样前端 | MMCM 90°/112.5° ✅ | 相同 MMCM 前端 + traceIF(width=2) |
| 去帧/解码 | unknown 1.76%, 13/15 ✅ | 待实测（2-bit TPIU 格式不同） |
| RTL 改造 | 当前裸字节直通 | 需接 traceIF（HANDOFF §7.2 #3） |

**本提案证明了**：网络和采样硬件在满速下没有瓶颈。2-bit 满速的剩余工作纯粹是 RTL 改造（接 traceIF）和相位优化——不存在不可逾越的物理障碍。
