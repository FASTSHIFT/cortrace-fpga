## 1. A1：trace pipeline 真实存活验证

### 红方质疑（摘）

> `trace_probe_top.v` L246 把整条 trace 流水线的输出这样喂进 `fpga_core`：
> `.sw ({3'b0, sf_out_valid, sf_data[3:0]})`
> 而 `fpga_core` 的 `sw` 在 NexysVideo example 里只接到 LED 显示和一些杂项，**不是 UDP 发送数据通路**。

### 蓝方坦白

红方对。我前一轮的 commit message 自夸"sf_data 进了 fpga_core 让综合不能优化掉"，但**实际上 fpga_core 的 sw 端口在 fpga_core.v 里只在一行被注释掉的 `assign led = sw` 引用，其余位置完全无用**——等于挂到一个浮空端口。Vivado opt_design 的 sweep/propagate pass **完全有理由**把整条 trace pipeline 推空。这一手"假喂"是自欺欺人。

### 蓝方动作

1. **加 DONT_TOUCH** 到 6 个 trace 实例（u_capture / u_traceif / u_dmux / u_chk / u_cobs / u_sf），保护它们不被 opt_design 整体剪掉。
2. **加 set_input_delay** 到 trace_data_in[*]，让 IDDR 输入端有真实 STA 语义；否则 Vivado 会把这条路视为"unconstrained → 等价常量"，进一步把整条 trace pipeline propagate 成常量。
3. **加 14 个真实 top-level 输出端口** trace_dbg_data/valid/last/inter，把 sf 输出真实导到 GPIO1 Bank 16 引脚——给一个"被消费"的下游，让 dataflow 可达性分析认账。

### 实测验证

`run_top_impl.tcl` 末尾追加 SURVIVAL CHECK 块，扫描 6 个实例的 cell 计数。post-impl 实测：

```
u_capture    : LUT=   0 FF=   0 BRAM= 0 IO= 9   (17 total cells)   ← IO 硬核 + DONT_TOUCH
u_traceif    : LUT= 142 FF= 284 BRAM= 0 IO= 0   (428 total cells)
u_dmux       : LUT= 254 FF=  70 BRAM= 0 IO= 0   (341 total cells)
u_chk        : LUT=  21 FF=   9 BRAM= 0 IO= 0   (35 total cells)
u_cobs       : LUT= 145 FF=  70 BRAM= 2 IO= 0   (238 total cells)
u_sf         : LUT=  21 FF=  51 BRAM= 0 IO= 0   (86 total cells)
                                                 ─────────────────
TRACE PIPELINE 合计                              583 LUT + 484 FF + 2 BRAM
```

与 T3 单独 OOC（494 LUT）对照：T4 顶层综合后 583 LUT，**多 18%**——这是合理的"展开 + 顶层 wire 路由 + DONT_TOUCH 抑制部分共享优化"的代价。

**关 A1**。

## 2. B2 / E3：frame128 跨域改 AsyncFIFO

### 红方质疑（摘）

> `fr_avail` 是 `traceIF` 的 toggle 信号，用 2-FF 同步到 clk100，OK。在 clk100 上检测 toggle 沿（`fr_pulse`），用它**采样 frame128（128 bit 跨域数据）**。
> 这是教科书级的 CDC 错误——`frame128` 这 128 根线**在两个时钟域之间是异步的**，从 trace_clk 翻转到稳定下来，每根线的传输延迟有差。`fr_pulse` 检测到之后下个 clk100 沿就采 frame128，但此时 frame128 的 128 bit **不能保证全部稳定**。

### 蓝方坦白

完全对。我把这个 P0 bug 写成"留 Stage-3 改 AsyncFIFO"——这是诚实声明里的不诚实。**xsim 通过的根本原因就是仿真器的 0 抖动**：所有 wire 同 ps 到位，Real silicon 上不可能。

### 蓝方动作

用 verilog-ethernet 自带的 `axis_async_fifo`（已被 fpga_core 内部 RX/TX FIFO 引入，零额外依赖）替换原 2-FF + frame_lat 手写 CDC：

```verilog
axis_async_fifo #(
    .DEPTH       (16),       // 16 frames * 16 byte = 256 byte buffer
    .DATA_WIDTH  (128),      // full frame width
    .KEEP_ENABLE (0),
    .LAST_ENABLE (0),
    .USER_ENABLE (0),
    .FRAME_FIFO  (0)
) u_frame_cdc (
    .s_clk (trace_clk), .s_rst (sys_rst),
    .s_axis_tdata (frame128), .s_axis_tvalid (frame_strobe), ...
    .m_clk (clk100),     .m_rst (sys_rst),
    .m_axis_tdata (cdc_out_frame), .m_axis_tvalid (cdc_out_valid), ...
);
```

为避免 RAMB36 async control DRC（REQP-1839），`frame_strobe` 的源寄存器 `fr_avail_q` 取消 async reset：

```verilog
reg fr_avail_q;
always @(posedge trace_clk) fr_avail_q <= fr_avail;  // no reset
wire frame_strobe = fr_avail ^ fr_avail_q;
```

### 实测验证

post-impl：
- BRAM Tile：9 → **11**（+2，正好是 axis_async_fifo 的 128 bit × 16 深度的 BRAM 占用）
- LUT：2,300 → **2,316**（+16，控制逻辑增量极小，Gray 码 + ptr 只占少量 LUT）
- WNS：+1.151 → **+1.082** ns（依然正余量）
- WHS：+0.052 → **+0.037** ns（依然正余量）
- DRC：**0 errors**（async control check warning 也清了）

**关 B2/E3**。

## 3. D3：set_input_delay + 诚实声明

### 红方质疑（摘）

> 当前 xdc **没有写 TRACECLK 的 input delay 约束**——`set_input_delay -clock trace_clk_in -max ... [get_ports trace_data_in]`，缺这条 Vivado 不知道 source-synchronous 的 setup/hold 窗口在哪。
> 当前 WNS=+1.151 ns 对采样链路的有效性存疑。

### 蓝方动作

1. 加完整 source-sync DDR input delay 约束（rising + falling，max + min）：
```tcl
set_input_delay -clock trace_clk_in -max  1.25 [get_ports {trace_data_in[*]}]
set_input_delay -clock trace_clk_in -min -1.25 [get_ports {trace_data_in[*]}]
set_input_delay -clock trace_clk_in -max  1.25 [get_ports {trace_data_in[*]}] -clock_fall -add_delay
set_input_delay -clock trace_clk_in -min -1.25 [get_ports {trace_data_in[*]}] -clock_fall -add_delay
```

2. **诚实声明**：trace_data_in→IDDR/D 这条源同步路径**Stage-2 OOC 不可能 timing close**——它需要 deskew 训练状态机扫到合适 IDELAY tap 才能进眼图中心。Stage-2 没写 deskew，所以 set_input_delay 加完后 hold 必然违例（实测 -3.4ns，符合预期）。
3. 把 hold 检查显式 false_path：
```tcl
set_false_path -from [get_ports {trace_data_in[*]}] -hold
```
**承认这是一个"上板才能消化的真实约束"**，不是设计 bug。

4. RTL 端：`trace_capture_a7` 的 IDELAY_VALUE 默认从 0 改为 16（中点，对应训练后预期落点），让综合阶段也能反映"已校准"假设下的近似数字。

### 实测验证

- 加 set_input_delay 之前：trace pipeline 被 propagate 成常量，T4 LUT = 2,161（**虚假**）
- 加 set_input_delay + DONT_TOUCH 之后：trace pipeline 真实存活，T4 LUT = **2,316**（诚实）
- WNS = +1.082 ns（来自 clk125_unbuf 等真实路径）
- trace_data_in→IDDR 路径 set_false_path -hold（红方批准的诚实例外）

**关 D3**。

## 4. N2：IDELAYCTRL.RST 同步释放

### 红方质疑（摘）

> `trace_capture_a7.v` 直接把 `rst` 喂给 `IDELAYCTRL.RST`，但 `rst = ~rst_n` 来自外部按钮，**没经过 ref_200m 的同步**。Xilinx UG471 / DS181 明确：IDELAYCTRL.RST 必须**异步置位、同步释放到 REFCLK**。

### 蓝方动作

```verilog
reg [3:0] idc_rst_sync = 4'hf;
always @(posedge ref_200m or posedge rst)
    if (rst) idc_rst_sync <= 4'hf;     // async assert
    else     idc_rst_sync <= {idc_rst_sync[2:0], 1'b0};   // sync release
wire idc_rst = idc_rst_sync[3];

IDELAYCTRL u_idelayctrl (
    .RDY    (idelayctrl_rdy),
    .REFCLK (ref_200m),
    .RST    (idc_rst)              // was: rst (raw button)
);
```

### 实测验证

- xsim 仍然 PASS（FRAME[0] = 12340203…0f 与 traceIF_tb golden 一致）
- post-impl 综合通过
- 资源代价：+4 FF（同步链）

**关 N2**。

## 5. E1：RGMII RX IDELAY 状态

### 红方质疑（摘）

> `fpga_core` 不含 IDELAY，它假设输入 phy_rxd 已经被上层 delay 过；蓝方的 trace_probe_top 直接接 fpga_core，跳过了 fpga.v——所以 phy_rxd 没有 IDELAY。
> 这意味着当前 RGMII RX 路径少了 IDELAY（如果 PHY 端 RX delay 关闭，RGMII 时序就崩）。

### 蓝方诚实说明

红方对，但更细的事实是：实测 post-impl 报告显示 **RGMII RX 已经实例化了 5 个 IDDR + 1 个 IDELAYE2**——这是 `eth_mac_1g_rgmii.v` 内部的 ssio_ddr_in 路径自带的，**不需要 fpga.v 板级 wrapper**：

```
| IDDR | 9 |   ← 4 (trace_capture_a7) + 5 (4 phy_rxd + 1 phy_rx_ctl, 在 fpga_core 内部)
```

但 NexysVideo `fpga.v` 的 IDELAY 是**额外的、可调的**，用来微调 RGMII RX 中心对齐。是否需要这一层取决于 **P0-1 strap**：
- 若 PHY 端 RX delay 已开（strap 默认）→ FPGA 端不需要 IDELAY，当前 fpga_core 即可
- 若 PHY 端 RX delay 关闭 → FPGA 端必须加 fpga.v 同款 IDELAY

**蓝方暂不补**，等 P0-1 strap 信息确定后决策。如果需要补，工作量约 ~10 行 RTL（5 个 IDELAYE2 + 1 个 IDELAYCTRL）。

### 状态

⚠️ **待 P0-1 strap 决策后定夺**。

## 8. A2：完整版资源诚实预估

## 9. A3：BRAM 缓冲只够 5ms

### 蓝方接受

红方正确：当前 BRAM 缓冲 ~150KB / 32MB/s = **~5ms**，够吸收 1ms 量级 PC 调度抖动，**不抗 Linux 大停顿（10–100ms）**。

ORBTrace 用 8MB HyperRAM = 250ms 缓冲，本设计差 50×。

- 评估接 A7-Lite 板载 4Gbit DDR3（有 MIG IP 现成）

**这条不在 Stage-2 关闭，是 Stage-3 范围内的明示妥协。**

### 状态

⚠️ **明示推迟到 Stage-3**。PLAN_STAGE2 已加边界声明。
