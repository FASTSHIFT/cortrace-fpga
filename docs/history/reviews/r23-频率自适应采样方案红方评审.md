> 立场：红方硬件架构评审。FPGA 时序分析、高速 IO、CoreSight trace 架构。

> 方法：逐条质疑，给具体技术论据/数据/文献。无法成立的质疑也诚实标注。

## 总裁决（先给）

方案 D 的工程思路（固定 MULT + PSINCDEC 相位微调）方向正确，但提案在 8 个关键点上存在**错误假设、遗漏风险、或工程不可行**的问题。最严重的三条：

1. PSINCDEC 步长公式写反，导致步长变化范围被低估 2×（14ps~28ps 不是"~20ps 均值"能覆盖的）。
2. 自校准 FSM 的锁定判据（sync 帧检测）在满载目标上可能**完全失效**——无 sync 帧就无法判断相位好坏。
3. 当前 1.7% unknown 的主要来源很可能不是相位偏差而是 SI/jitter 本底——PSINCDEC 精度再高也压不下去。

**评审不否定方向，但要求蓝方在落地前解答以下 8 条。**

## Q1 · MMCM PSINCDEC 的真实行为：步长公式与变化范围

### 蓝方声称

> "PSINCDEC 步长 = 1/(56×VCO_freq) 秒。VCO=630M→步长=28.4ps；VCO=1260M→步长=14.2ps"
> "相位分辨率 ~20ps（PSINCDEC @ VCO≈840M 均值）"

### 质疑

**蓝方的公式 `1/(56×f_VCO)` 是正确的**（UG472 Table 3-6："Phase shift increment = 1/(56 × f_VCO)"，即 VCO 周期的 1/56）。但"~20ps 均值"这个表述**严重误导设计**。

实际变化范围：
- VCO=630 MHz（TRACECLK=42M）：步长 = 1/(56×630M) = **28.3 ps**
- VCO=840 MHz（TRACECLK=56M）：步长 = 1/(56×840M) = **21.3 ps**
- VCO=1260 MHz（TRACECLK=84M）：步长 = 1/(56×1260M) = **14.2 ps**
- VCO=1440 MHz（TRACECLK=96M）：步长 = 1/(56×1440M) = **12.4 ps**

**步长变化 2.28×（12.4ps ↔ 28.3ps）**。对 eye-scan 一致性的影响：

1. **满圈步数不同**：42M 时满圈 = T_TRACECLK / step = 23.8ns / 28.3ps = **840 步**；84M 时满圈 = 11.9ns / 14.2ps = **838 步**（几乎相同，因为满圈步数 = 56 × DIVID = 56×15 = 840，是常数，这点蓝方算对了）。
2. **但 eye-scan 的物理分辨率不同**：84M 时 UI=5.95ns，840 步扫一圈意味着每步覆盖 5.95ns/840 = 7.1ps 的时间窗。42M 时 UI=11.9ns，每步覆盖 11.9ns/840 = 14.2ps。**低频时每步的相对分辨率更粗**（占 UI 的比例相同，但绝对时间窗不同，影响 jitter tolerance 的解读）。
3. **关键遗漏**：UG472 注明 PSINCDEC 精度是 ±50ps（DS181 Table 49: "MMCM Phase Shift: Min increment ±50ps (Estimate)"）。当 VCO=1260M 时标称步长 14.2ps，**±50ps 的不确定性超过了 3 个步长**。这意味着在高 VCO 端，PSINCDEC 的实际位置不确定性**可能吃掉你以为找到的"最优"相位**——你扫到的"最优步"和真实 eye center 之间的误差可能高达 ±50ps。

**对设计的影响**：
- 84M（产品重点频段）VCO=1260M，步长 14.2ps，±50ps 不确定性 ≈ ±3.5 步。FSM "找最低 unknown 的位置"得到的步数有 ±3.5 步抖动——如果 eye opening 只有 ~2ns（proposal 22 实测 84M 相位差 22.5° 就差 100× unknown，即 eye 很窄），±50ps 已经是 eye opening 的 ~2.5%，**不致命但也不是忽略项**。
- **蓝方应标注**：PSINCDEC 精度不是"~20ps 分辨率"而是"标称 14-28ps 步长 ± 50ps 累积不确定性"。设计 FSM 时的 THRESHOLD 和 CHECK_FRAMES 必须容忍这个不确定性。

### 裁决

**部分成立**。公式本身正确，但"~20ps 均值"是工程误导。要求补充 ±50ps 不确定性对 eye-scan 判据的影响分析。

## Q2 · MULT=15 的 timing closure 风险：VCO=1260M 高端 jitter

### 蓝方声称

> "MULT=15: 84M→VCO=1260M(✓)"
> "风险: 低（MMCM 参数固定，只调相位步进）"

### 质疑

VCO=1260M 在 Artix-7 speed grade -1（DS181 Table 49 / UG472 Table 3-1）的 VCO 范围是 **600-1200 MHz**；speed grade -2 是 **600-1440 MHz**。**蓝方用的板子是什么 speed grade？**

如果是 -1（最常见的 Artix-7 成本优化芯片）：
- VCO=1260M **超出规格**（>1200M）。MMCM 可能能 lock（Xilinx 留有余量），但属于超频使用，**不保证 timing、不保证温度范围内稳定**。
- 即使是 -2（VCO 上限 1440M），1260M 在 1440M 上限的 87.5%——**接近上限但有余量**。

**高 VCO 下的 jitter 恶化**（DS181 Table 49, "Output Jitter"）：
- 7 系列 MMCM 的 output jitter 随 VCO 频率和 MULT 增大而增大。具体公式见 Xilinx UG472 附录 A（Jitter Calculation）。
- **经验值**：VCO=1260M、MULT=15 时，output peak-to-peak jitter 典型 ~80-150ps（取决于输入 jitter、bandwidth 设置等）。DS181 Table 49 的 "MMCM Output Jitter (peak-to-peak)" 典型 100ps。
- **对采样的影响**：84M DDR 的 UI = 5.95ns。MMCM output jitter 100ps pp = UI 的 **1.7%**。加上 PCB skew + STM32 output jitter，total timing budget 中 MMCM jitter 占多少？

**计算**：
- 总裕量 = UI/2 = 2.975ns（从 edge 到 eye center）
- 减去：STM32 trace output skew（DS9405 Table 34: tsk(trace) max = 2ns @168MHz）
- 减去：PCB propagation skew（杜邦线，估计 0.3-1ns）
- 减去：MMCM jitter（~50ps RMS → ~100ps pp）
- 减去：IDDR setup/hold（DS181: 0.2ns）
- **剩余**：2.975 - 2.0 - 0.5 - 0.1 - 0.2 = **0.175ns = 175ps**

**这已经极其紧张**。而且上面的 STM32 tsk=2ns 是 4-bit mode 的，如果实际 skew 接近 max spec，**已经没有裕量了**。

**关键问题**：蓝方提案说"风险：低"——但实际上 VCO=1260M 意味着你已经把 timing budget 吃到只剩 ~175ps 裕量。**PSINCDEC 的 ±50ps 不确定性已经吃掉这个裕量的 28%**。这不是"低风险"。

### 裁决

**成立**。MULT=15 @ 84M → VCO=1260M 不是"低风险"。要求蓝方：
1. 确认 speed grade（-1 则 VCO 超规格，不可接受）
2. 给出完整 timing budget 分析（含 STM32 output skew + PCB + MMCM jitter + IDDR setup）
3. 考虑 MULT=10（VCO=840M，当前已实测 golden）作为 84M 的默认值，只有需要覆盖 <56M 时才用 MULT=15

## Q3 · 自校准 FSM 的锁定判据：sync 帧在满载下可能不出现

### 蓝方声称

> "利用 traceIF 的 sync 检测（`REsyncPacket || FEsyncPacket`）作为质量指标——能连续检测到 TPIU sync 帧 = 相位正确"

### 质疑

**TPIU sync 帧（0x7FFFFFFF）的出现频率取决于 TPIU formatter 的空闲程度。** 根据 CoreSight TPIU-Lite TRM（DDI0298B）§3.3：

> "The formatter inserts synchronization requests into the data stream whenever possible... The synchronization pattern is 32 bits of logic 1 followed by logic 0."

关键词："whenever possible"。TPIU sync 只在有空闲时隙时插入。当目标 CPU 满载运行（ETM 持续产生 trace 数据、FIFO 从不空闲）时：

1. **TPIU formatter 可能长时间不插 sync**——因为 ETM 数据流持续占据所有时隙。
2. ARM IHI0029 (CoreSight Architecture Specification) §6.2.1 规定 sync 的最小间隔 = 128 bytes，但**最大间隔没有上限保证**（取决于实现和数据流密度）。
3. **proposal 22 § 15-frequency-sweep-plan §14.3 已经实测**："FSYNC=0, HSYNC(FF 7F)=551 个"——在部分捕获中 **FSYNC 为零**！这直接证明蓝方自己的数据里 sync 帧可以不出现。

**后果**：如果目标 CPU 满载运行（这恰恰是"实时 profiling"最想抓的场景），FSM 的 `sync_detect` 可能一直为 0——**FSM 无法判断相位是否正确，永远扫不到 LOCKED 状态**。

**更糟的情况**：FSM 在 LOCKED 状态后，用 `continuous_sync_loss > TIMEOUT → rescan` 做温漂检测。如果正常运行时 sync 就极少出现（满载），FSM 会**误判为失锁**，触发不必要的 rescan——造成 trace 中断。

### 备选判据建议

1. **HSYNC (0xFF7F) 计数**：proposal 22 §15 实测 HSYNC 密度 ~245/6KB，远比 FSYNC 密集。HSYNC 是 TPIU 半同步字，在正确对齐时以固定间隔出现。**用 HSYNC rate 做质量指标更可靠。**
2. **bit-level 统计**：正确采样时 4-bit nibble 的值分布应相对均匀（P-header 的 atom 编码空间覆盖 0x0-0xF）；错误相位时某些 bit 固定为 0/1（stuck bit）。**用 nibble 方差做快速质量指标。**
3. **A-sync 计数器**：traceIF 内部的 `remainingClocks` 状态是否持续正常递减（不卡住/不溢出），可作为"流结构健康"的指标。
4. **CRC（如果有）**：我们的流没有 CRC，但如果加一个简单的 running XOR parity 到 FPGA 采集端，可以做帧级校验。

### 裁决

**成立，且致命**。自校准 FSM 的核心判据（sync 帧检测）在产品最重要的使用场景（满载 profiling）下可能完全失效。要求蓝方：
1. 换用 HSYNC 或其他不依赖 TPIU 空闲的判据
2. 给出判据在"连续满载 ETM 流"下的 worst-case 可用性证明
3. 分离"相位锁定"和"温漂检测"两个 FSM 状态的判据——锁定用密集 HSYNC，温漂检测可以更宽松

## Q4 · scan 期间的数据丢失：~1.7ms 校准窗口的 trace 完全不可用

### 蓝方声称

> "全圈扫描：840 步 × 2μs = ~1.7ms"
> "实际（eye 宽度 >30% → 找到就停）：~0.5ms"
> "产品形态：上电自动校准 ~5ms 完成"

### 质疑

**每次 PSINCDEC 步进时，IDDR 的采样时钟瞬间跳变一个步长（~14-28ps）。在跳变瞬间（1 VCO cycle ≈ 0.8-1.6ns），IDDR 采到的数据是无效的**（采样点可能正好在 data eye 边沿）。

但更重要的是：**在整个扫描期间（840 步 × 每步切换 + 检测），FPGA 没有稳定的采样点——它在逐步移动相位。** 这意味着：

1. **整个 ~1.7ms（worst case）到 ~0.5ms（best case）校准期间，trace 数据全部丢失。**
2. 对于"上电自动校准"场景：可以接受——目标可能还没开始执行关键代码。
3. **对于"温漂重校准"场景：不可接受**——目标正在全速执行，trace 正在实时流式传输给 profiling 工具。触发 rescan = **强制 trace 中断 0.5-1.7ms**。

在 84M 4-bit DDR 下，1.7ms 丢失的数据量 = 84M × 1B/cycle × 1.7ms = **142,800 bytes**。对于一个函数级 profiling 场景，这可能是数千个函数调用的执行流丢失。

### "不停流"校准方案是否可行？

理论上可以做"background tracking"：
- 锁定后不动主采样时钟（clk_sample）
- 用一个独立的"影子"CLKOUT（CLKOUT2，也接 PSINCDEC）做后台相位扫描
- 影子 CLKOUT 驱动一个独立 IDDR 做质量监测
- 只在影子扫描确认更优相位后，一次性切换主采样时钟

**但 7 系列 MMCM 的 PSINCDEC 只能作用于所有 CLKOUT 或单个指定的 CLKOUT**（UG472 Table 3-6: PSCLK/PSEN/PSINCDEC 是全局端口，但可以通过 CLKOUT_PHASE_SHIFT 选择哪个 CLKOUT 受影响）。所以技术上可以用 CLKOUT1 做采样、CLKOUT2 做影子扫描——**前提是 MMCM 的 PS 端口可以配置为只影响 CLKOUT2**。

查 UG472 §3 "Dynamic Phase Shift"：MMCME2_ADV 的 PS 功能可以配为 VARIABLE（selected output）或 VARIABLE_POSITIVE。**但一个 MMCM 实例的 PS 只作用于一个 CLKOUT**（通过 `CLKOUTn_USE_FINE_PS` attribute 选择）。所以如果你把 FINE_PS 给了 CLKOUT2（影子），CLKOUT1（主采样）就不受 PS 影响——**可以实现"不停流"的影子扫描**。

**但代价是**：需要多一路 IDDR + 采样逻辑（资源翻倍不多，~100 LUT），以及切换逻辑（确认影子找到更优点后，通过 DRP 一次性调整 CLKOUT1 的静态 phase——**这又需要 MMCM reset，数据丢失回来了**）。

### 裁决

**部分成立**。上电校准的 1.7ms 丢失可以接受。但温漂重校准的数据丢失对"连续实时 profiling"场景是真实问题。蓝方应：
1. 量化"温漂重校准频率"——如果一天才触发一次（温度变化慢），0.5ms 中断可能可接受
2. 考虑"影子扫描"架构作为 Phase 3 增强
3. 在产品需求里明确标注"校准期间 trace 中断 0.5-1.7ms"的 tradeoff

## Q5 · 温漂重校准的触发条件：sync_loss 不能区分"温漂"和"程序行为变化"

### 蓝方声称

> "state LOCKED: if continuous_sync_loss > TIMEOUT: goto SCAN // 温漂等导致失锁，重扫"

### 质疑

**`continuous_sync_loss` 有两种完全不同的物理来源：**

1. **温漂导致相位移出 eye**：sync 帧的 bit pattern 被错采 → 检测不到 sync → `sync_loss` 递增。这是蓝方想检测的。
2. **目标程序从 idle 变满载**：ETM 数据流持续占满 TPIU 带宽 → TPIU 不插 sync → `sync_loss` 递增。**这不是温漂，是程序正常行为变化。**

**FSM 无法区分这两种情况。** 后果：
- 程序进入一段密集计算（无 sync 帧）→ FSM 误判温漂 → 触发 rescan → **trace 中断 0.5-1.7ms（Q4）**
- 更糟：rescan 完成后回到 LOCKED → 程序仍在满载 → sync 仍不出现 → **又触发 rescan → 反复中断**

**这是一个活锁（livelock）风险**：在满载场景下，FSM 可能在 LOCKED↔SCAN 之间反复跳转，导致 trace 间歇性不可用。

### 解法

1. **不用 sync_loss 做温漂触发**。用 MMCM 的 LOCKED 信号：如果 MMCM 本身失锁（LOCKED=0），那才是温漂/频率变化。但 MMCM 失锁意味着 VCO 已经跑飞——此时 phase 已经无意义了，应该做 full re-init 而非 phase scan。
2. **用 error rate 做温漂触发**（如果有在线 error 检测）：在 LOCKED 状态持续监测采样质量（HSYNC 密度、nibble 统计），**只有质量指标恶化超过阈值才触发**。关键：这个"质量"不能依赖 sync 帧（回到 Q3 的问题）。
3. **温度传感器**（如果有）：Artix-7 内置 XADC 温度传感器。温度变化超过 ΔT 阈值时触发 re-scan——直接监测物理原因而非间接症状。**这是最可靠的触发方式**，且与程序行为完全解耦。

### 裁决

**成立**。`sync_loss` 不能区分温漂和程序行为变化，满载下有活锁风险。要求蓝方换用不依赖 TPIU sync 的触发条件（XADC 温度传感 或 HSYNC-rate/nibble 统计的质量退化）。

## Q6 · 和 2-bit 路径的兼容性：33% unknown 的独立问题

### 蓝方声称

> "WIDTH 参数保持：traceIF 路径（WIDTH=2）和 raw 路径（WIDTH=4）不受影响"

### 质疑

提案 proposal 22 §7.4 + proposal 25 的数据表明：
- 4-bit 84M raw 路径（不过 traceIF）：unknown 1.7-2.5%，可工作
- 2-bit 路径（过 traceIF(WIDTH=2)）：**unknown ~33%**（HANDOFF 里记录的数字，已确认是 a/b swap + 时钟域问题）

**2-bit 的 33% unknown 问题不是相位问题**——它是 traceIF 逻辑层的 a/b 配对错误或时钟域交叉问题。方案 D 的 PSINCDEC 相位微调**对这个问题完全没有作用**。

蓝方说"WIDTH 参数保持不受影响"——但这恰恰是问题：2-bit 路径有独立的对齐问题（与 PSINCDEC 无关的 a/b swap + CDC），方案 D 不能"一并解决"它，需要独立处理。

**具体技术问题**：
1. traceIF.v 在 `always @(posedge traceClkin)` 里直接用 `traceDina`/`traceDinb`——这是在 traceClkin 域里操作。如果 traceClkin 是 MMCM 的 CLKOUT1（phase-shifted），而 traceDina/traceDinb 来自 IDDR（也由 CLKOUT1 驱动），那么它们天然同步。
2. **但 2-bit 模式的实际问题可能是**：在 2-bit 时 traceIF 的 `construct` shift register 的 nibble 组装逻辑与 4-bit 不同，而且 TPIU 2-bit 格式的 half-sync（`0xFF7F` 在 2-bit nibble 流里的对齐方式）可能与 4-bit 不同——**这是帧层逻辑问题，与相位无关**。

### 裁决

**成立（但不致命）**。方案 D 不能解决 2-bit 的 33% unknown 问题——这需要独立的 traceIF(WIDTH=2) 逻辑调试。蓝方应明确声明"方案 D 只解决 4-bit 路径的相位校准问题，2-bit 有独立的帧对齐 bug 需要单独修"。

## Q7 · 与上游 orbtrace 对比的公平性：源同步 vs MMCM 的架构必要性

### 蓝方声称

> "我们的方案在分辨率和自动化程度上优于上游"

### 质疑

**上游 orbtrace 是源同步（source-synchronous）架构：TRACECLK 直接驱动 IDDR 采样数据。** 这意味着：
- 数据和时钟共享同一信号源（STM32 TPIU）
- PCB trace 长度匹配后，skew 天然很小
- **根本不需要 MMCM**——TRACECLK 本身就是最好的采样时钟

从 traceIF.v 源码可以直接看到：`always @(posedge traceClkin)` 里 `traceDina`/`traceDinb` 就是 IDDR 在 TRACECLK 双沿采出的数据。**没有 MMCM、没有相位调整、没有 PSINCDEC**。

**为什么我们不能也走源同步？** 回顾 proposal 22 §10.2-10.3 和 PLAN_STAGE4 的历史：

1. **低频问题**：proposal 22 §10.3 的分析指出，Artix-7 IDDR 在低频时"无 ECP5 天然偏移"——直接用 TRACECLK 沿采样 = 采在 data 边沿（eye 最差）。ECP5 的 IDDRX1F 有内置 delay 使采样天然偏移到 eye center；**Artix-7 IDDR 没有这个特性**。
2. **IDELAY 补不动**：proposal 22 §2 证明 IDELAY 只有 2.5ns 范围，低频时 half-UI 远超 2.5ns → IDELAY 补不到 eye center。
3. **MMCM 相位偏移是 workaround**：用 MMCM 把 TRACECLK 移相 90°（或 112.5°）来人为制造"采样偏移"——相当于用 MMCM 模拟 ECP5 IDDRX1F 的天然偏移。

**但这引出关键问题**：

- **如果我们的目标频段是 40-96M（proposal 26 声称）**：在这个频段，half-UI = 5.2-12.5ns。IDELAY 的 2.5ns 范围在 50M+ 已经接近够用了（half-UI=5ns 时 IDELAY 能覆盖到 eye center = 2.5ns 处）。**>60M 时 IDELAY 就能直接到 eye center**。
- **所以对 84M（核心目标频率）**：half-UI=5.95ns，eye center=2.975ns。IDELAY 31 tap = 2.4ns < 2.975ns，**差一点点（0.575ns ≈ 7 taps）**。但如果用 IDELAY 63 tap 模式（需要改 refclk 到 300MHz 或用级联）或加一点 MMCM 粗偏移...

**真正的问题**：MMCM 架构引入了不必要的复杂性吗？

**不完全是**。因为：
1. **纯源同步在 Artix-7 上确实有 setup/hold 问题**：Artix-7 IDDR 的 clock-to-output 路径没有 ECP5 那个~2ns 的内置 delay。直接用 TRACECLK → BUFG → IDDR，数据和时钟的 skew 完全取决于 PCB + IO buffer delay。如果这些 delay 恰好落在 eye center 附近（碰运气），就能工作；否则需要校准。
2. **MMCM 是"可控的源同步"**：MMCM 锁定在 TRACECLK 上（频率跟踪），然后提供一个可调相位的采样时钟——**本质上仍是源同步（时钟来自 TRACECLK），只是加了相位调整能力**。
3. **上游 orbtrace 在 ECP5 上"碰运气式"工作**（proposal 22 引用的 testbench 注释 "don't worry about phase"）——**这不是好的工程实践，只是在 ECP5 上碰巧 timing 落在眼内**。我们的 MMCM 方案是更可控的工程做法。

**但比较的公平性问题**：蓝方说"我们的分辨率优于上游"——这个比较没有意义。**上游不需要分辨率，因为它的采样时钟就是数据时钟（零 skew 理论值）**。比"分辨率"就像比"谁的轮子更圆"——人家骑自行车不需要轮子特别圆也能走，你造摩托车需要精密车轮，但你不能说"我的轮子比自行车圆所以我更好"。

### 裁决

**部分成立**。
- MMCM 架构本身是 Artix-7 上的合理工程选择（不是"不必要的复杂性"）
- 但与上游的对比不公平——应该说"我们在 Artix-7 上需要 MMCM 相位调整来弥补它相对 ECP5 的源同步缺陷"，而不是说"我们分辨率优于上游"
- 如果将来换一个有 IDELAY 级联或 ISERDESE2 的方案，MMCM 可能就不需要了

## Q8 · 1.7% unknown 的真实来源：PSINCDEC 压不下去的本底

### 蓝方声称

> "预期可将 unknown 从当前的 2-4% 压到 <0.5%（精确对准 eye center）"

### 质疑

**这是提案中最关键的未证实假设。** 让我用现有数据检验：

proposal 22 §7.5 已经做了精细相位扫描：
- 21M @ PHASE=90.0°：unknown **0.002-0.005%** ← 接近完美
- 84M @ PHASE=112.5°：unknown **0.009-0.012%** ← 也接近完美（proposal 22 报的值）

但 proposal 25（本次满速流式验证）报告：
- 84M @ PHASE=112.5°：unknown **1.76%** ← 差 100×

**同一个频率、同一个相位，为什么 proposal 22 报 0.01% 而 proposal 25 报 1.7%？**

可能的解释：
1. **proposal 22 是 one-shot 60KB 窗口**（proposal 22 §7.5 用的是 BRAM 捕获，~60KB）
2. **proposal 25 是 20MB 流式捕获**（proposal 25 "捕获数据 20 MB"）
3. 流式模式引入了新的 error source：FIFO CDC、packetiser、网络传输中的 bit flip...

**但即使排除传输问题**，proposal 22 的 0.01% 是在"最优条件"下（短窗口、刚上电、温度稳定）。长时间流式运行时：
- **温漂**：芯片温度从 25°C 升到 60°C 时，IO delay 变化 ~100-300ps（Artix-7 典型）
- **电源噪声**：长时间运行时 VCC aux 纹波增大，影响 MMCM jitter
- **STM32 侧 jitter**：长时间满载运行时 STM32 的 PLL jitter 可能增大

**更根本的问题**：如果 PHASE=112.5° 是 proposal 22 的"最优"（0.01%），而方案 D 的 PSINCDEC 能做到比 4.5° 步长精细——那 PSINCDEC 最多能把 0.01% 压到... 还是 0.01%（因为 112.5° 已经是 one-shot 最优了）。**PSINCDEC 不会比 proposal 22 的静态最优 phase 更好。**

**那 1.7% 的增量（1.7% - 0.01% = 1.69%）来自哪里？**
- 不是相位偏差（112.5° 已是最优）
- 很可能是**SI 本底噪声**：长流式运行中的间歇性 nibble slip（proposal 22 §14-16 大量篇幅分析的"散布 ~1KB 脏窗口"）
- Proposal 22 §14 的结论："偶发 ~1KB 局部去帧失锁窗口,散布在捕获各处" + §16 "奇数个 nibble 的插入/丢失（漏采/多采一个 TRACECLK 边沿）"

**这意味着**：1.7% unknown 的主要来源是**物理层的间歇性 nibble slip**（边沿质量/jitter/SI），不是相位偏差。PSINCDEC 精确对准 eye center **对 nibble slip 毫无帮助**——因为 slip 发生在 jitter 尖峰瞬间，不是稳态相位偏差。

**证据链**：
- proposal 22 §13：实测 TRACECLK 有 **5ns 级 runt/毛刺**（min dwell=1 ref cycle）
- proposal 22 §14.1："偶发 nibble 插入/丢失" = 边沿被 jitter 推过采样点
- proposal 22 §18：无缝帧行走器把 unknown 从 ~10% 压到 0.00%（解码侧消化了 nibble slip）

**结论**：proposal 22 已经用解码侧（walk 重锁）把 one-shot 的 unknown 压到了 0.00%。但 proposal 25 的 1.7% 是在**没有 walk 重锁的 raw 流上**测的（orbetto 路径没有我们的 walk 解码器）。

**所以问题的正确分解是**：
- **稳态相位偏差**：已由 PHASE=112.5° 解决（0.01% 级）。PSINCDEC 能做到一样好，但**不会更好**。
- **间歇性 nibble slip（SI/jitter 本底）**：这是 1.7% 的主要来源。**PSINCDEC 对此无效**。只能靠：(a) SI 改善（短线/阻抗匹配板）(b) 更强 RTL 去毛刺 (c) 解码侧 walk 重锁。

### 蓝方"压到 <0.5%"能实现吗？

- **如果指的是 raw 流（不经 walk 解码）**：不能。1.7% 的主要来源（nibble slip）不受 PSINCDEC 影响。
- **如果指的是经 walk 解码后**：已经是 0.00% 了（proposal 22 §18），PSINCDEC 对此也没有增量贡献。
- **PSINCDEC 的真实价值是**：免去手动扫 PHASE（proposal 22 §7.5 每频率要手动扫），实现**自动化**——但不是"压低 unknown"。它的产出是**工程便利性**（一个 bitstream 覆盖多频率、自动找最优），不是**误码率改善**。

### 裁决

**成立，这是提案最大的逻辑漏洞。** 蓝方把"精细相位分辨率"等价于"更低 unknown"——但实测数据证明 1.7% unknown 的主要来源不是相位偏差（静态最优相位已实测到 0.01%）。PSINCDEC 的价值在自动化和多频率覆盖，**不在压低 unknown**。要求蓝方：
1. 删除"压到 <0.5%"的预期（或限定为"one-shot 短窗口在 PSINCDEC 自动找到最优相位后可达 <0.5%，等价于 proposal 22 手动最优"）
2. 明确声明：流式 1.7% 的残余是 SI/jitter 本底 + nibble slip，PSINCDEC 不解决这个问题
3. 把方案 D 的价值重新定位为"工程自动化 + 多频率覆盖"而非"误码率改善"
