## 一句话结论

> **提案 35 的核心承诺"换上游极简结构 → 一次性消除三个坑 → 解码变好"已经在 doc 16 里被蓝方自己证伪了。** doc 16 的 `CAP_RAW=0 traceIF 帧路径`实测**就是**这个提案要移植的结构（IDDR + 同域 traceIF 组帧 + 128-bit 整帧原子跨域），文中白纸黑字"三个坑全消失"，结果**照样 99.7% 非法**。所以三个坑既已消除、质量却没变好——这直接说明**根因不在三个坑，也不在自造前端**。提案把这条已经跑过的路当成"没试过的新方案"重卖，且回避了它最致命的前提：**上游"不管相位"依赖 ECP5 IDDRX1F 固有输入延迟，Artix-7 IDDR 没有**——裸 IDDR@BUFG 采在 edge-aligned 数据的跳变点，相位靠什么，提案没有答案。

## R1 🟥 阻断 — 提案的收益承诺已被 doc 16 的 CAP_RAW=0 实测证伪（归因崩塌）

**实测（doc 16，蓝方自己的数据）**：doc 16 §"traceIF 帧路径实测（CAP_RAW=0）"记录的链路是

```
trace_capture_a7(IDDR) → traceIF.v(同 trace 域组帧) → 128-bit 整帧存储
```

这与提案 35 §3 的数据流**本质相同**（IDDR → traceIF@trace域 → 128-bit 帧原子跨域）。doc 16 对该次实测的原话：

- "**HSYNC 自动滤除、无 CDC 撕裂、无 nibble 偏移**（CAP_RAW=1 的三个坑全消失）"
- "**但质量差**：严格判据非法事件率 **99.7%**（INSTR_RANGE=10 vs RESERVED=2764）"

**因果链拆解**：提案 35 §5 承诺"一次性消除 doc 16 记录的三个坑，因为它们都来自自造前端"。但 doc 16 证明：**三个坑在 CAP_RAW=0 帧路径里已经消除了，非法率仍是 99.7%**。于是：

> 三个坑 = 已消除；质量 = 没变好。**⇒ 三个坑不是 99.7% 的根因。** 提案把"消除三个坑"当作"解码会变好"的因果，逻辑断裂。

**判决**：**归因不成立**。提案 §5"预期收益"和 §6 风险表"当前 37 PC / 99.7% 非法 → 缓解：替换后复测"是**循环论证**——它假设的东西（换上游就好）正是 doc 16 已经否掉的。

**要求（root）**：提案必须先解释"CAP_RAW=0 帧路径已经是上游结构、已消三坑、为何仍 99.7%"，再谈移植。否则这是把跑过的实验换个名字重跑。

## R2 🟥 阻断 — 最致命前提未答：Artix-7 裸 IDDR 的采样相位靠什么

**实测（源码）+ 推断（强）**：
- `glue.py`：`DDRInput(clk=traceclk, ...)` + `ClockSignal().eq(traceclk)` —— 上游确实纯 IDDR@TRACECLK、无 IDELAY、无过采。
- `traceIF_tb.v` 注释原文："**Fortunately, CORTEX-M always sends LSB on L-H edge, so we don't need to worry about phase.**" —— 这是**功能仿真**里"不管相位"（仿真无 setup/hold），**不是**硬件上不管相位。
- 提案 §4 自己承认："上游能'不管相位'是因为 ECP5 IDDRX1F 有固有输入延迟把采样推入眼内。**Artix-7 的 IDDR 没有**——直接在 TRACECLK 边沿采 = 采在 edge-aligned 数据的跳变点（doc 14 §22）。"

**问题**：提案承认了这个前提失效，然后 §4 的"赌注"是"**先按裸 IDDR 实测，不够再补**"。但这正是 doc 16 已经做过的（CAP_RAW=0 就是裸 IDDR@BUFG + traceIF），结果 edge-aligned 采在跳变点 → 每周期都可能采错半位 → 帧内容错 → 99.7%。**提案没有给出"这次裸采为什么会比 doc 16 的裸采好"的任何机制差异。**

edge-aligned + 裸 IDDR@BUFG 的物理事实（推断，强）：TPIU 数据沿与 TRACECLK 沿对齐，IDDR 在 C 的两个沿采样 = 采在**数据正在翻转的时刻**，setup/hold 双违例。BUFG 还带全局插入延迟与 skew，使采样点相对数据的相位**不可控且不在眼内**。这与 r26 R3 观察的 `0x5=0x1|0x4` 跨周期位混叠是同一类现象。

**判决**：**提案把一个"ECP5 特有、Artix 不成立"的前提当普适方案**。§4 的"再补"选项（单全局 IDELAY / 90° 相移）见 R5，本身也没论证充分。

**要求（root）**：在写 RTL 前，必须回答"Artix 裸 IDDR 采样相位如何落进眼内"，并给出**与 doc 16 CAP_RAW=0 的机制差异**。若无差异，提案 = doc 16 已否结果的重放。

## R3 🟥 阻断 — 丢/漏 TRACECLK 边沿是"采样完整性"问题，换上游同域组帧不会自动修复

**实测（doc 16 结论）**：doc 16 末尾自己定位——"字节序**基本对**（10 个真 A-sync 检得到）；99.7% 非法是 **A-sync 之间的数据坏 = traceIF 组帧丢/漏 TRACECLK 边沿**（IDDR@48M 采样质量），不是字节序……即 IDDR 在此频率是否漏采边沿导致帧不连续。"

**因果拆解（推断，强）**：
- 若 IDDR 在 48M 漏采/多采 TRACECLK 边沿（相位差导致亚稳/串扰误判），则 `traceIF` 的 36-bit `construct` 移位寄存器**每漏一拍就整体错位**，其后所有 packet 边界、sync 计数、`elemCount` 全部滑移 → 帧内容系统性错 → A-sync 之间全坏。
- 提案 35 的上游结构**同样在 TRACECLK 域组帧、同样用 IDDR 采样**。"漏边沿"发生在**采样点**（IDDR@edge-aligned），不在字节 CDC。**换上游的 AsyncFIFO 整帧跨域，改变的是"帧组好之后怎么过域"，根本碰不到"帧组之前边沿采样是否完整"。**

**判决**：提案把一个**采样完整性**故障，寄望于一个**跨域原子性**改动去解决——**作用点错位**。换完极大概率**还是 99.7%**（因为 doc 16 的 CAP_RAW=0 已经是这个结构且就是 99.7%）。

**要求（root）**：提案必须给出"上游结构为什么不漏边沿"的因果，而不能只说"上游简单所以好"。若答案是"上游靠 ECP5 固有延迟不漏"——那就回到 R2，Artix 没有。

## R4 🟥 阻断 — traceIF 在 48–200 MHz TRACECLK 域的时序收敛未做 STA；不收敛则组帧本身错

**实测（RTL 阅读）**：`traceIF.v` 全部逻辑在 `always @(posedge traceClkin)`，单拍内包含：
- 36-bit `construct` 移位；
- 两个 32-bit 比较（`REsyncPacket`/`FEsyncPacket`，且 `FEsyncPacket` 是 width 三路 mux 的 32-bit 等值比较）；
- 16-bit `packet` 的多路选择（isREsync × width）；
- `elemCount` 递减 + 8 路 `case` 把 16-bit 写进 112-bit `cFrame`；
- 128-bit `Frame` 拼装。

**推断（强）**：这坨组合逻辑（多个 32-bit 比较器 + 128-bit 扇出）在 100 M+ TRACECLK（周期 ≤10 ns）上 Artix-7 (-1/-2 speed grade) **很可能收不敛**。上游 orbtrace 跑的是 SWO/较低频 trace，没有 100–200M 并口的先例。**提案 §6 风险表把"高频 traceIF 时序收敛"列为风险却写"实测；必要时流水化"——即承认没做 STA。**

**判决**：若 traceIF 在目标频率 setup 违例，**组帧结果本身就是错的**，与前端采样、与 CDC 都无关。这是提案能否成立的独立必要条件，目前空白。

**要求（root）**：综合后给出 `traceIF` 在 48/100/150/198 MHz 的 STA（WNS/TNS）。若不收敛，先流水化 traceIF（会改变帧时延但不改内容），再谈移植。这一步**可以纯 OOC 综合完成，不必上板**。

## R5 🟨 高风险 — 回退路径"单个全局 IDELAY / 90° 相移"与 proposal 22/33 的既有结论冲突，疑似兜圈子

**实测（proposal 22/33）**：
- proposal 22/26：IDELAYE2 总范围 ~2.4 ns（31 tap × ~78 ps）。对 84M 半位 5.95 ns 勉强够偏移，对更低频半位远不够；且"相位随频率变"。
- proposal 33（RETIRED）：per-lane IDELAY 校准上板后"错误率反而抖"，被撤销，结论是"别再走 IDELAY 校准回头路"。
- r26 R3：`0x5/0xa` 错误"对 IDELAY tap 完全不敏感"——即**故障在 IDELAY 够不着的下游**。

**推断**：提案 §4 回退选项 a"单个全局固定 IDELAY 把 4 lane 一起延迟 ~1/4 UI 进眼内"：
1. 全局单值无法补 lane 间相对 skew（proposal 33 的教训）；
2. 1/4 UI 在不同频率对应不同绝对延迟，单固定值不能跨频（proposal 22 的范围问题）；
3. r26 已实测"移整体延迟对这个错误无效"。
选项 b"90° 相移 MMCM"提案自己也标注"引入 gap 失锁问题，慎用"（与"停走时钟 gap 容忍"需求直接冲突，见 §6 风险表）。

**判决**：两个回退选项要么被既有实验否过（a），要么与本项目的 gap 容忍需求冲突（b）。"先裸采、不够再补"极可能一步步补回 `trace_capture_a7` 那套复杂度——**兜圈子风险高**。

**要求**：回退路径需正面回应 proposal 33 的 RETIRED 结论与 r26 的 tap-无关实测，说明"这次为什么不一样"。

**诚实标注**：此条是"路径风险"，非"必然失败"。若 R2/R4 先解决且实测证明单全局 IDELAY 在固定频率下够用（可能，对单一目标频率而言），则本条可降级。

## R6 🟨 高风险 — 验收判据缺可复现激励，"非法率"数字目前无意义

**实测（doc 16）**：当前 37 PC 的会话"A-sync 只有 10 个"。真 ETM 的 A-sync 密度、INSTR_RANGE 数量受 firmware、BB、TRACECLK、采样窗口时长共同影响。

**推断**：在激励不固定的情况下，"非法事件率 < 5%"这个验收数字**不可比也不可复现**——换一次抓样，A-sync 数、事件总数就变，分母漂移。r25（对 proposal 34 的评审）已经批过"集合去重 + 非固定激励"的虚荣指标问题。

**要求（root，且低成本）**：验收前先固定**可复现测试激励**：
- 已知程序（func_test，固定编译产物，ELF 与 flash 严格一致）；
- `BB=1`、固定 TRACECLK（如 48M）、固定采样字节数；
- 报告 (INSTR_RANGE, RESERVED, BAD_SEQUENCE, NOT_SYNC, TRACE_ON) 全套 + 连续正确指令段中位数（非集合去重）；
- 与 doc 16 的 12M/781 PC 会话**同激励**对照。

否则"< 5%"无法判定达标与否。

我跑了上游自带 `verilog/testbeds/traceIF_tb.v`（iverilog 12.0）：


**结论（实测）**：`traceIF` 在**理想双沿输入、无 SI、无漏边沿**下组帧 100% 正确，字节序 big-endian 原序（与 doc 16 标定一致）。**⇒ 组帧逻辑本身没问题；99.7% 必来自"喂给 traceIF 的 trace_a/trace_b 序列已经错了"，即采样完整性（漏/多边沿）。** 这直接支持 R3：问题在采样点，不在组帧、不在跨域。

### 验证 B（待做，1 天，纯仿真）— 给 traceIF 喂"漏一个边沿"的序列，看是否复现 A-sync 之间全坏

改造 `traceIF_tb.v`：在正确 TPIU 帧流中**故意丢 1 个 TRACECLK 周期**（模拟 IDDR 漏采一沿），观察 sync 之后 `construct` 是否整体错位、后续帧是否全非法。若复现 doc 16 的"A-sync 附近对、之间全坏"签名，则**根因 = 漏边沿**被坐实，与前端换不换上游无关。

### 验证 C（待做，纯 OOC 综合）— traceIF 在 48/100/150/198M 的 STA

对 `traceIF.v` 单独跑 OOC 综合 + 时序（R4）。给出 WNS。这一步决定 traceIF 要不要先流水化，**在写 top 之前就能知道**。

**只有 A/B/C 通过（组帧对、漏边沿是根因且能定位、traceIF 高频收敛），写 `trace_upstream_top.v` 才有意义。** 否则大概率重演 doc 16 的 99.7%。

- 提案的**归因**（三个坑来自自造前端 → 换上游消坑 → 解码变好）被蓝方自己的 CAP_RAW=0 实测击穿：**三个坑已消，仍 99.7%**。
