## 一句话裁决

**17 §6 的"字节零误码"扎实（🟩），但最关键的那条"帧从没被 FPGA 发出来"是从主机计数器反推的推断，而项目里明明有一个直接测源头丢帧的硬件计数器（`stream_lost_cnt`，RTL 我读了，实现正确、接线正确），却因为读出坏值被搁置——用反推代替了唯一的直接证据。18 号 DDR 方案 P0 说这个计数器"可能没实现对"，是错的：RTL 是对的，坏的是主机在满速流下走共享 `:5001` 路径读它（会超时/读到 stale）。整个 DDR 架构压在一个从没实测的前提上——"CoreMark 平均 trace 率 < 千兆线速"。这个前提用 10 分钟就能测（endurance 已经打印平均速率），却拿"~50-110MB/s 多数 < 千兆"这种拍脑袋数据搪塞——而它自己给的上界 110MB/s 距 118MB/s 线速只剩 7% 余量，一旦平均超线速，DDR 只治突发不治平均，整条 RTL 路白走。动 RTL 前，先修 lost_cnt 的读法（不是 RTL）、实测平均 vs 峰值率、并把已排除的多线程/recvmmsg 收流补测一次。**

## 17 §6 逐条

### 主张 1："是丢帧不是坏帧"（NIC errors=0 / InCsumErrors=0 / ramp monotone）🟡 **部分成立，覆盖面有漏**
- **实测且可信**：到达帧字节全对（ramp 逐字节 monotone、坏帧=0、8MB 抽样解码 INSTR_RANGE 56206 PC 100% flash）。这证明**到达的帧**字节零误码。🟩
- **漏洞（红方命中）**：ramp monotone 只校验了**到达帧的帧内字节连续性**，**没校验跨 seq-gap 的字节连续性**——因为丢帧处 seq 跳号，ramp 计数器在缺口两侧本就不连续，无法用来判"缺口里那些帧是否也曾字节正确"。所以"坏帧率=0"严格只覆盖"到达的帧"，**对丢失的帧的内容无从判断**（这在丢帧场景下无所谓，但不能反推"物理层字节永远零误码"）。
- **更重要的漏洞**：AGENT.md 坑点 17/21 记录过采集侧 nibble 错位/半字节错，且**同一抓样坏包率会 0.75%→10% 漂移**（采集质量依窗口变）。这次 NIC errors=0 只说明**这次采集窗口质量好**，不能推广成"字节零误码是链路稳态属性"。**判据补强**：需在**已知会漂到高坏包率**的窗口重测一次坏帧率，确认坏帧=0 不是挑了个好窗口。
- **依据**：实测（到达帧），但"零误码"的普适性是推断。

### 主张 2："CPU pin 无效 → 不是收流端" 🟥 **证伪该推断：pin 生效性未验证，且单线程 recvfrom 是未排除的瓶颈**
- **实测**：pin 前 0.013%、pin 后 0.0135%（几乎不变）。
- **致命漏洞 1（pin 是否真生效未验证）**：文档没给任何"进程真的在 core15 上跑、真的是 SCHED_FIFO"的验证（`taskset -p` / `chrt -p` / `/proc/PID/stat` 的 processor 字段）。**pin 无效 ≠ pin 没生效**——如果 `chrt`/`taskset` 因权限或写法没实际生效，那 0.013%→0.0135% 只是"两次没 pin 的抖动"。
- **致命漏洞 2（单线程 python recvfrom 本身是瓶颈）**：收流是**单线程 Python `recvfrom` 逐包**（`stream_endurance.py` 主循环）。110k pps / 116MB/s 下，单线程 Python 每包 Python 字节码开销 + GIL，**这本身就可能是瓶颈**，而 pin 到一个核**救不了单线程处理速率**——pin 只防迁移/抢占，不提升单核吞吐。所以"pin 无效"完全可能是"瓶颈在处理速率不在调度"，而**换 C / recvmmsg（批量收）/ 多线程 / AF_PACKET 才是对的杠杆**。
- **"不是收流端"这个结论下早了**：pin 无效只排除了"调度抢占"这一种收流端问题，**没排除"单线程处理速率不足"**。而 RcvbufErrors=0 也不能排除——见主张 3。
- **依据**：实测数字真，但"不是收流端"是**过度归纳的推断**。

### 主张 3（最关键）："主机全环节零丢 + seq 有缺口 → 帧从没被 FPGA 发出" 🟥 **证伪为"唯一解释"；测量方法有多个漏洞**
这是全篇的支点，也是最脆的一环。

- **rx_dropped "新增 0" 的时机问题（红方命中）**：文档说"之前有 26628 drops，这次新增 0"。但 `rx_dropped` 是**读两次求差**——如果两次读的间隔恰好、或读到的是缓存/上次窗口值，"新增 0"可能是**测量窗口错位**。**没有给出读取时机与流量窗口的对齐证据**。之前 26628、现在 0，中间变量（backlog 250000）改过——**backlog 加大后 NIC 层确实可能不丢了，但这不等于"没丢包"，只是丢包点移到了别处**。
- **漏查的内核计数器（红方命中，且是硬漏洞）**：文档只查了 NIC rx_dropped / UDP RcvbufErrors / InErrors / InCsumErrors。**没查**：
  - `/proc/net/softnet_stat`（第 2 列 dropped、第 3 列 time_squeeze）——**软中断 backlog 丢包，110k pps 高发区**；
  - `tc -s qdisc`（qdisc 层 drop）；
  - `IgnoredMulti`（文档自己提到之前非 0 = 5967，**这个数从没解释**）；
  - `netstat -su` 的 `InError`/`SndbufErrors`/`packet receive errors` 全量。
  - **"全环节零丢"是在只查了 4 个计数器的情况下下的——至少 3 类丢包点没查。**
- **seq-gap → "从没发出"是唯一解释吗？🟥 不是**。至少三个未排除的替代：
  1. **FPGA seq 计数器跳号**：`seq <= seq + 1'b1` 只在包完成时递增（我读了 RTL，line 690），正常不会跳；但若 self-TX FSM 在 8ms underrun abort（fpga_core_net line 547）后重启，**seq 是否连续未验证**——abort 路径可能丢一个包但 seq 行为需确认。
  2. **softnet backlog 丢包**（上面）——帧发出了、到了 NIC、但在软中断入队时被丢，`rx_dropped` 不一定涵盖这个（那是 driver ring 层）。
  3. **单线程 recvfrom 漏收**：内核收了、socket buffer 有、但 Python 没及时 recv 导致 buffer 满——**但 RcvbufErrors=0 说 buffer 没满**……除非 RcvbufErrors 也是时机问题（同 rx_dropped）。
- **依据**：**纯推断**（"反推"是文档自己的用词）。项目有直接测源头丢帧的硬件计数器 `stream_lost_cnt`，却因读出坏值不用，改用主机计数器反推——**这正是"用推断代替单步坐实"的本项目惯犯模式**。

### 主张 4："ramp 恒速也丢 0.017% → 不是 ETM 突发" 🟡 **部分成立，但与"上次零丢"矛盾未解释**
- **红方命中的矛盾**：§1 说"之前 ramp 573MB / 5s 零丢"，§6 说"这次 ramp 60s 丢 0.017%"。**同样 ramp，一次零丢一次丢**。蓝方拿"这次丢"证明"源头缓冲问题"，那"上次零丢"怎么解释？
  - 变量差异：573MB/5s = **秒级**，60s = **分钟级**；backlog 改过；`.245` 配置；**CSR poll 干扰**（stream_endurance 每 interval poll :5001 lost_cnt）。
  - **最可疑：CSR poll 抢占**。文档 §5 自己承认"`:5001` poll 会被满速 `:5555` 流淹"（坑点 25）。`read_lost_cnt` 每 interval 发一个 :5001 请求——**这个请求走的是与 self-TX 共享的 TX 路径**（fpga_core_net 仲裁：RX-echo 优先，self-TX 让路）。**每次 poll 都会让 self-TX 暂停一下去服务 :5001 echo**，正好可能造成源头 FIFO 在那一刻积压→溢出。**"ramp 恒速也丢"完全可能是 poll 自己造成的**，而不是链路固有。
  - **上次零丢的 573MB 测试没有 poll**（是 `probe stream-link` 单次），这次有 poll——**这恰好是两次差异的最大变量**，蓝方没控制它。
- **判据补强**：ramp 跑一次**完全不 poll lost_cnt** 的 60s（甚至 1h），看还丢不丢。若不丢 → 丢包是 poll 自造的，DDR 方案的前提（源头 FIFO 太小）**直接崩塌**。
- **依据**：实测数字真，但因果（源头缓冲 vs poll 抢占）**未隔离**，是推断。

## 18 号 DDR 方案逐条

### 主张 5："DDR 数百 MB 缓冲能让平均<线速时真零丢" 🟥 **核心赌注，前提未实测**
- **"CoreMark 平均 trace 率 < 千兆"从没实测**。§3.3 写"4-bit@100M BB=0 实测平均 ~50-110MB/s，多数<千兆"——**这个"实测"没有出处**，且 endurance 明明打印了平均速率（B 真 trace = 111MB/s！见 §6.1 表）。**111 MB/s 已经是平均速率**（20003MB/180s），距线速 118MB/s **只剩 6%**。这不是"多数<千兆"，是"平均已逼到线速鼻尖"。
  - ⚠️ **注意**：111MB/s 是 self-TX **打包后**的线速（含 seq 头 + UDP/IP/eth 帧头），不是纯 trace 净荷率。但即便折算净荷，**平均率距线速余量极小**，DDR"平均<线速则永不满"的前提**濒临破产**，必须实测纯 trace 净荷平均率 vs 线速净荷上限。
- **MIG DDR3 并发读写可持续带宽 >> 118MB/s 双向 未实测**：§6 风险表说"MIG @400MHz ~数 GB/s，读写各半仍够"——**这是理论峰值**。持续并发读写同一 ring 的**实际**带宽要扣：刷新（~1-2%）、读写切换 turnaround、行激活/预充电、页命中率。**从没跑过 `ddr3_selftest` 的并发读写实测**（文档自己把它列为"待确认"）。118MB/s 双向 = 236MB/s，DDR3-800 x16 理论 1.6GB/s，账面够，但**并发小突发访问模式下的实效带宽可能腰斩**，未验证。
- **环形 buffer 持续并发读写是全新场景，"复用现成 async FIFO 已处理"是过度复用假设 🟥**：`la_ddr_writer/reader` 是为**离线 dump**（写满一次→读一次，proposal 32 blackbox）设计的。**"writer 持续写 + reader 追着 wr_ptr 持续读同一 ring"是全新并发场景**：wr_ptr/rd_ptr 跨 3 时钟域（clk200 capture / MIG ui_clk / clk125 net）实时追赶、回绕检测、读写不撞——**这些在离线 dump 里根本不存在**（dump 时写完才读，无并发）。说"已处理"是把离线件的正确性**无根据地外推**到并发场景。这是 r31 批过的"把'已实现'当'已验证'"同型问题。
- **依据**：全推断。核心前提（平均<线速）被 §6.1 自己的 111MB/s 数据**反证濒临破产**。

### 主张 6："P0 先修 lost_cnt 就能量化源头丢帧" 🟥 **误诊 lost_cnt 坏因；RTL 是对的**
- **我读了 RTL**（`trace_stream_top.v:651-661`）：
  ```verilog
  reg [31:0] lost200 = 32'd0;
  wire drop = cap_valid & ~fifo_in_ready & ~selftest_active;
  always @(posedge clk200) if (drop) lost200 <= lost200 + 1'b1;
  // CDC to clk125, assign stream_lost_cnt = lost_125;  映射到 NB+34..37
  ```
  **计数器实现正确、语义正确（cap_valid 但 FIFO 不接受 = 丢）、接线正确（映射到 DEPTH+34..37）**。18 号 §7 说它"可能没实现对/没连对信号"——**错，RTL 没问题**。
- **坏值 30665081 的真因（我的诊断）**：
  1. **host offset 假设 DEPTH=61440**（`read_lost_cnt` 用 `depth+34`）。**如果实际烧的 bit 的 DEPTH 参数不是 61440**，offset 就指向别的寄存器/BRAM 数据 → 读出垃圾。**先确认运行 bit 的 DEPTH**。
  2. **:5001 读出在满速 :5555 流下不可靠**：`:5001` echo 与 self-TX **共享 TX 路径**（fpga_core_net 仲裁），且 CAP_RAW BRAM 读有**1 周期 stale**（fpga_core_net line 400-406：首字节重复 source[base]）。满速流下 echo 可能超时/返回 stale/被 abort（8ms underrun guard）。`stream_endurance` 的 poll "超时就跳过"——**读到的可能是碰巧返回的错位字节**。
  3. **每 interval 涨 ~3000 万**：这不是随机垃圾，是**规律性错位**——高度像"读到了流数据的某几个字节"而非 lost 计数器。
- **正确的 P0**：不是"改 RTL 修计数器"，是**修读法**——用一个**不与满速流争用**的读取时机（比如短暂暂停 self-TX 再读，或用独立的低频状态端口），并**先核对运行 bit 的 DEPTH**。RTL 一行都不用动。
- **依据**：18 号对 lost_cnt 坏因的判断是**未读 RTL 的推断**，实测（读 RTL）证伪。

### 主张 7："先 DDR 不上重传" 🟡 **路线选择合理性依赖前提 5，前提未证则过早**
- **逻辑链**："DDR 吸收突发 → 若平均<线速则零丢 → 不需重传"。**整条依赖主张 5 的前提（平均<线速）**，而该前提被 §6.1 的 111MB/s 反证濒危。
- **若平均逼近/超线速**（4-bit@100M 峰值可能就超，文档自己承认），DDR 只治突发不治平均——**整条 RTL 路白走**，最后还是得降位宽/降频/BB=0 过滤。那**为什么不先花 10 分钟测平均率**，确认 DDR 前提成立再动几天的 RTL？
- **过早排除的更简单路（红方命中，都没试）**：
  - **recvmmsg 批量收**：一次 syscall 收多包，单线程即可大幅降 per-packet 开销——**直接针对主张 2 未排除的"单线程 recvfrom 瓶颈"**。
  - **多线程收流 / SO_REUSEPORT 多 socket**：多核并行收。
  - **AF_PACKET + mmap ring（PACKET_RX_RING）**：绕过 UDP 栈，零拷贝收。
  - **降位宽到 2-bit**：平均率直接减半，若平均是问题这是最省的解（不动收流、不动 DDR）。
  - **这些全在"动 RTL 写 DDR ring"之前该试**——它们是软件/配置改动，小时级可验证，而 DDR ring 并发化是数天 RTL + 跨 3 时钟域调试。
- **依据**：路线选择是推断，且**没有对比过更便宜的备选**。

## (a) 哪些"实测结论"测量方法有漏洞、要补什么

1. **"帧没被 FPGA 发出"（主张 3）**——最关键，靠反推。**补**：(i) 修 `stream_lost_cnt` **读法**（核对运行 bit DEPTH + 找不与满速流争用的读取时机），直接读源头丢帧数；(ii) 补查 `/proc/net/softnet_stat`、`tc -s qdisc`、`IgnoredMulti`、`netstat -su` 全量；(iii) 每个计数器读取与流量窗口**时间对齐**（记录读取时刻 + 前后流量）。
2. **"CPU pin 无效"（主张 2）**——**补**：`chrt -p <pid>` / `taskset -p <pid>` 确认真生效；换 **recvmmsg** 收流复测同一场景，看丢包是否变——这直接判"是不是收流端"。
3. **"ramp 恒速也丢"（主张 4）**——**补**：跑一次**完全不 poll lost_cnt** 的 ramp（60s+），隔离 CSR poll 抢占。若不 poll 就不丢 → 丢包是自造的。
4. **"字节零误码"（主张 1）**——**补**：在已知会漂到高坏包率（0.75%→10%）的窗口重测坏帧率。

## (b) 动 DDR RTL 前必须先做的最便宜证伪实验

**决定 DDR 方案成不成立的前提 = "CoreMark 平均 trace 净荷率 < 线速净荷上限"。这个 10 分钟能测：**
- 用 `stream_endurance` 已有的平均速率打印，跑 5-10 分钟真 trace，记录**平均线速率**（已知 111MB/s）**和瞬时峰值率**（加窗口统计 max）。
- 换算成**纯 trace 净荷率**（扣 seq 头 4B + UDP/IP/Eth 头 ~42B / 1028B 包 ≈ 4.5%）。
- **判据**：
  - 平均净荷率明显 < 线速净荷（比如 <90MB/s）→ DDR 前提成立，可继续（但仍要先做 §a 修 lost_cnt）。
  - 平均净荷率 ≈ 或 > 线速净荷 → **DDR 方案作废**，直接走降位宽（2-bit）/降频/BB=0，别写 RTL。
- **同时**：跑 `ddr3_selftest` 的**并发读写**带宽实测（不是只读或只写），确认 >> 236MB/s 双向。这是 DDR ring 可行性的硬前提，也是 RTL 前该测的。

## (c) 被过早排除的更简单路（都没试）

1. **recvmmsg 批量收流**——最该先试，直接打主张 2 未排除的单线程瓶颈，纯软件、1 小时可验。
2. **多线程 / SO_REUSEPORT 多 socket 收流**。
3. **AF_PACKET + PACKET_RX_RING（mmap 零拷贝）**。
4. **降位宽到 2-bit**——若平均率是根因，这是最省解，不动收流不动 DDR。
5. **关掉 CSR poll 跑纯流**——0 成本，可能直接消除 §6.4 的丢包。

## 最后一句话给用户

**别急着动 DDR RTL。物理层零丢这个目标，当前第一个该补的实验是"关掉 lost_cnt 的 :5001 poll、跑一次纯 ramp"——因为你文档里自己承认 poll 会淹流，而它恰好是"上次 573MB 零丢、这次 60s 丢 0.017%"两次唯一没控制的变量；如果不 poll 就不丢，那所谓"FPGA 源头 FIFO 溢出"根本不存在，DDR 方案的前提当场崩塌。紧接着第二件事是 10 分钟测 CoreMark 平均 trace 净荷率 vs 线速——你 §6.1 自己的数据是平均 111MB/s、距线速只剩 6%，DDR"平均<线速就零丢"的赌注已经悬了，一旦平均超线速，DDR 只治突发不治平均，几天 RTL 白写。而且 stream_lost_cnt 的 RTL 我读了是对的（drop=cap_valid & ~fifo_in_ready，接线正确），坏的是你在满速流下走共享 :5001 路径读它、加上 host 的 DEPTH offset 假设——修读法不用动一行 RTL。在这三件（不poll的ramp、平均率实测、修lost_cnt读法）+ 补查 softnet_stat/qdisc + 试一次 recvmmsg 之前，DDR ring 并发化（跨 3 时钟域、把离线 dump 件当并发件复用）是典型的"没坐实就动最贵的 RTL"。**
