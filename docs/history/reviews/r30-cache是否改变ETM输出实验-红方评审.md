## 一句话裁决

> **总结论"cache 改数据本身、非仅速度"未被证据支撑，是又一次把速度的二阶后果包装成更深机制。** 三条证据：A 是速度效应（双方无争议）；**B 样本量=1 的 SysTick 异常，是"cache 跑得快 → 546µs 内恰好跨过一次 1ms SysTick 边界"的纯速度二阶后果，不是数据本质变**——我复核日志确认 ON=1/OFF=0，且这正好是"覆盖时间跨度"效应；**C 是拿手册"存在这种机制"冒充实测——我在两份 packet 日志里 grep，Cancel/Mispredict/推测/微架构异常元素数量都是 0/0，C 声称的机制在实测数据里根本没出现**。更致命的是**单变量纯度破产**：两个 `mem.bin`（喂解码器的程序镜像）MD5 不同、大小差 128 字节、2615 字节有差异——**这是两个不同二进制，"只切 cache"不成立**，B 的"异常落点差异"完全可能来自地址布局不同。用户真正想问的是 (ii) cache 改没改架构执行路径；文档全程只证明了 (i) trace 流长相不同，却用词让人以为证明了 (ii)。

## 一、证据 A/B/C 逐条判定

### 证据 A — 同窗口净数据 2.8×　✅ **成立（但与主张无关）**
50M/BB=1 同窗口，cache ON deframed 10778 vs OFF 3790（我核对 `/tmp/d50con/etm.bin`=10778B、`/tmp/d50coff/etm.bin`=3790B，与文档一致）。这是**纯速度效应**：cache OFF 时 CPU 等 flash、trace 稀疏。文档自己也归为速度效应、非争点。**判定成立，但它证明的是"跑得快 → 同时间更多包"，恰恰支持"只是速度"，不支持"数据本质变"。**

### 证据 B — cache ON 有 1 个 SysTick 异常、OFF 无　🟥 **证伪其作为"数据本质变"的论据**
**复核**：我 grep 两份日志——`g50con.log` SysTick=1、EXCEPTION 相关=2 行（一进一"ret addr follows"）；`g50coff.log` SysTick=0、EXCEPTION=0。数字属实。

**但这恰恰证伪主张，理由三层**：

1. **样本量=1**。用 0 vs 1 一个事件去论证"cache 改变异常插入位置"，统计上不成立。换一次抓样窗口相位，OFF 也可能抓到 1 个、ON 抓到 0 个。

2. **这是纯速度的二阶后果，不是数据本质变**。SysTick 是 **wall-clock 固定周期中断**（HAL 默认 1ms=1kHz；窗口 546µs）。546µs < 1ms，所以**一个窗口内期望跨过 SysTick 的次数 ≈ 0.5 个**——本来就是"有时抓到 0、有时抓到 1"的边界情形。cache ON 执行位置/时刻不同，恰好这一窗口跨过了一次 SysTick 边界；OFF 没跨到。**"异常出现"完全是"窗口在 wall-clock 时间轴上恰好覆盖了一个 SysTick tick"的结果——这是覆盖时间跨度效应，属速度族，不是"cache 让 ETM 生成了本不存在的数据类型"。** 红方 Q2 的假设成立：蓝方把速度的二阶后果偷换成"数据内容变"。

3. **SysTick 本身与 cache 无因果**。SysTick 中断由 SysTick 定时器按 CPU 周期计数触发，cache 开关不改变 SysTick 是否发生、发生频率（wall-clock 1ms 恒定），只改变"这个 546µs 快照恰好落在哪两个 tick 之间"。所以异常包的**有无**是采样窗口相位的抽签，不是 cache 对 trace 数据的作用。

**判定**：数字属实，但**推论证伪**。B 不能证明"cache 改变 trace 数据本身"，它证明的是"快照窗口相位抽中了/没抽中一个周期性中断"。文档把它列为"强证"是错的。

### 证据 C — 手册:推测执行(MAXSPEC=1)+微架构异常　🟥 **引用属实，但拿"可能性"冒充"实测证据"**
**核验引用**：`ddi0494d.txt` §2.4.10（line 1932-1934）"Micro-architectural exceptions … `0b0000100001 Entered a restricted region`"——**属实**；TRCIDR9 MAXSPEC（line 6547-6550）"Maximum trace speculation depth is one"——**属实**。引用无造假。

**但这是致命的方法论错误**：C 只证明"ETMv4 架构里**存在**推测/微架构异常机制"，**完全没证明"本实验中 cache 通过它们改变了输出"**。我直接在两份 packet 日志里搜：
```
Cancel / Mispredict / speculation 元素：  g50con=0, g50coff=0
微架构异常 (restricted region 等)：       g50con=0, g50coff=0
```
**C 声称的所有机制，在实测数据里出现次数全是 0——ON 和 OFF 都没有。** 既然 ON/OFF 都是 0，这些机制**根本没有随 cache 变化**，谈何"cache 通过它们改变输出"。这是红方 Q3 精确命中的问题：**拿手册"存在这种机制"冒充"实测证据"**。

**判定**：引用属实，但作为"cache 改数据"的证据**证伪**——机制在数据中零出现，无差异，不构成任何支撑。

## 二、单变量纯度裁决　🟥 **破产（隐藏第二变量：不同二进制）**

红方 Q1 命中要害。我核对喂给解码器的程序镜像：
```
md5  /tmp/d50con/mem.bin  = 91c20dd8...   size 43732
md5  /tmp/d50coff/mem.bin = 47e1217a...   size 43604   (差 128 字节)
cmp -l 逐字节差异 = 2615 处
```
**两个 `mem.bin` 是两个不同的二进制**（`SCB_EnableICache/DCache` 调用 + `-DBOARD_ENABLE_CACHE` 条件编译改变了代码/地址布局），大小差 128B、2615 字节不同。文档 §1 声称"两个固件仅差 `-DBOARD_ENABLE_CACHE`……其余全同""严格单变量：只切 cache"——**不成立**。

**后果**：
- **B 的异常落点差异被污染**：两个二进制地址布局不同，`0x8009436` 的返回地址、SysTick 落在哪段代码，本就因布局不同而不同。B 观察到的"异常有无/位置"无法归因于 cache，因为**二进制本身就变了**。
- **A 的 2.8× 也部分被污染**：不同二进制的指令数、分支结构可能不同（虽主因仍是 flash 等待，但不是纯净对照）。
- 文档反复强调的"严格单变量纪律"（本项目一贯卖点）在这份实验里**实际破坏了**，且蓝方**没有意识到**——用两个不同 ELF 分别解码，把"不同二进制"当成了"同一程序的 cache 开关"。

**判定**：单变量声称证伪。这是比 A/B/C 更根本的方法论缺陷。

## 三、(i) vs (ii) 概念裁决　🟥 **偷换概念**

红方 Q4 命中。两种"cache 改变 trace 输出"：
- **(i) 弱**：trace 流的字节/包序列不同（跑得快自然多包、窗口相位不同自然异常有无不同）。
- **(ii) 强**：cache 改变了**程序的架构执行路径 / 执行了哪些指令**——这才是用户真正问的"cache 到底动没动 trace 的**本质**"。

**ARM 架构上 cache 对软件透明**：cache 命中/未命中**不改变架构执行结果**（执行哪些指令、分支方向、寄存器/内存最终值）——它只改**时序**。这是 ARMv7-M 架构的基本保证。

**蓝方的证据全部落在 (i)**：
- A = 更多包（速度）→ (i)
- B = 异常包有无（窗口相位抽签）→ (i)
- C = 手册机制，实测零出现 → 什么都没证
- 文档自己诚实排除的 unique-PC 集合差异，本来是唯一**指向 (ii)** 的方向，却（正确地）判为弱证。

**所以蓝方没有任何证据表明 cache 改变了"执行了哪些指令"(ii)**，却用"cache 改变 trace 输出数据本身"这种措辞让人以为证明了 (ii)。§0 结论"cache 不是对 trace 透明的"是**误导性表述**——cache 对**架构执行**透明（(ii) 不变），只对**trace 流的时间展开/采样窗口内容**不透明（(i)，且这是速度和窗口相位的平凡后果）。**判定：偷换概念。**

## 五、总结论裁决

**"cache 改变 trace 数据本身、非仅速度" — 未被证据支撑，证伪。**

- 用户真正的问题是 (ii)：cache 动没动架构执行路径。**答案（架构上）是：不动**（ARM 保证 cache 对架构执行透明）。
- 蓝方证据全落 (i)：更多包（速度）、异常包有无（窗口相位抽签）、手册机制（实测零出现）。**没有一条触及 (ii)。**
- 加上单变量破产（两个不同二进制），连 (i) 层面的"异常落点差异归因于 cache"都不成立。
- **正确结论应是**：cache 主要改**速度**；速度 + 采样窗口相位会让**同一 546µs 快照的 trace 流长相不同**（包多少、恰好covered哪个 SysTick tick），但这不等于 cache 改变了程序执行的指令序列。cache 对 BB=0 假调用的真实作用回到 r29 已定的**"cache 全速 → 锚点物理间距拉大 → 盲推漂移"**——那是**速度经由锚点密度**的间接作用，仍是速度族，不是"cache 往 trace 里注入了新的数据机制"。

## 六、下一步唯一最该做的验证

**优先级 1（先修方法论，否则一切白测）：同一二进制、运行时切 cache。**
- **做法**：编**一个**固件（单一 ELF/单一 `mem.bin`），把 cache 开关做成**运行时**分支——例如读一个 GPIO/DIP 或一个 `volatile` 全局，上电后 `if (flag) SCB_EnableICache/DCache;`。两次运行烧**同一个 .bin**、用**同一个 ELF** 解码，只有运行时那一个 bool 不同。
- **判据**：`md5sum` 两次的 `mem.bin` 必须**相同**（否则又不是单变量）。此时地址布局、指令序列完全一致，任何 trace 差异才真能归因于 cache。

**优先级 2（在单一二进制上，直接测 (ii) 而非 (i)）：wall-clock 对齐 + 逐指令 diff。**
- **做法**：用 **BB=1**（精确、不盲推）+ **相同的执行起点锚**（如从某个函数入口 A-sync 开始）+ **相同的指令条数窗口**（不是相同 wall-clock 时间——那会引入 SysTick 相位差；改成"从入口起 N 条 INSTR_RANGE"），比较 cache ON/OFF 的**指令序列是否逐条一致**。
- **判据**：若同起点、同 N 条指令内，ON/OFF 的 PC 序列**逐条相同**（异常按各自 wall-clock 落点插入除外）→ **证明 cache 对架构执行透明（(ii) 不变）**，用户问题的答案就是"只改速度、不改执行路径"。若出现**架构层面**的指令序列分歧（非异常、非溢出）→ 那才是"cache 改数据本质"，需报 ARM 级异常。

**优先级 3（若要坐实证据 C 的机制，必须抓到差异，不能只引手册）：**
- 在单一二进制上，grep packet 日志的 `Cancel`/`Mispredict`/微架构异常元素，**给出 ON vs OFF 的计数差**。当前实测是 **0 vs 0**——在拿到非零差异前，C 不能作为任何证据。**判据**：ON/OFF 计数有统计显著差异（非样本量=1）才成立。

**关于是否需要 packet-level / Cancel 元素**：需要，但它是**优先级 3**，且前提是先做**优先级 1（同一二进制）**。在两个不同二进制上抓 Cancel 差异毫无意义（差异会被布局混淆）。而且当前数据里 Cancel=0/0，说明这条路大概率抓不到东西——M7 MAXSPEC=1、50M 低频推测窗口极小，**不要指望它是主因**。

## 一句话给用户

**这个实验没能证明它的结论。用户真正想问的是"cache 动没动程序的执行路径（执行了哪些指令）"——ARM 架构保证 cache 对执行结果透明，只改时序；而蓝方三条证据全落在"trace 流长相不同"这个平凡层面：A 是跑得快包更多（速度），B 那个 SysTick 异常样本量只有 1、而且 546µs 窗口本来就是"有一半概率跨过一次 1ms SysTick"的抽签，纯粹是速度让窗口恰好覆盖了一个中断，不是 cache 往 trace 里注入了新东西，C 更离谱——我把两份 packet 日志 grep 了一遍，它引用手册说的推测执行/微架构异常元素，实测里 ON 和 OFF 都是 0 个，机制根本没出现，是拿"手册里存在"冒充"实验里发生"。最要命的是所谓"只切 cache"根本不成立：两个解码用的镜像 MD5 都不一样、差了 128 字节、2615 处不同——是两个不同二进制，B 看到的异常落点差异完全可能是地址布局变了。要真回答用户，先编一个固件、用运行时 bool 切 cache（两次烧同一个 .bin、同一个 ELF 解码），然后用 BB=1 从同一个函数入口起、比同样多的指令条数，看 PC 序列逐条是否一致——一致就证明 cache 只改速度不改执行路径，这才是用户问题的诚实答案。**
