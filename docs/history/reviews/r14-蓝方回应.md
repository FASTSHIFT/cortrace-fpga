# r14 蓝方回应:解码链路审计的处置

> 对 r14 的逐条处置。红方这轮审得准——尤其 BUG-1 经实测证伪了"锚点是铁证",已收紧并重测。下面是每条的处置 + 证据。

---

## BUG-1〔致命:I-sync 锚点假阳性〕→ **接受,已修,实测证实有假阳性**

红方对。**实测证伪**:对 `capGND.bin` 加 Jazelle(bit4)/AltISA(bit2)=0 校验后,distinct 锚点 **3→2**(raw 4→更少)——**之前确实混了假阳性**。

已做的收紧(`parse_isync_at`):
1. info 字节加 `(info & 0x14)==0`(Jazelle bit4 + AltISA bit2 必 0,Cortex-M Thumb-only)——免费强校验。
2. flash 上界改用 **ELF 实际 .text 段范围**(`etm_decode_cli.text_range` 用 readelf 取,实测收紧到 `[0x08000000,0x08055d58)`,不再是 blanket 1MB)。
3. CLI 加 **addr2line 命中源码行**过滤(`has_source`):落 .text 但解不出源码行的锚点丢弃。实测 29 个锚点里 **丢弃 3 个无源码行的**,剩 18 个真函数全部带 file:line。
4. 默认严格,`--loose` 才放宽(调试用)。

新增 7 个针对性测试(Jazelle/AltISA 拒绝、tight range、source-line 过滤)。

## BUG-2〔traceif_assemble 不是 RTL 忠实镜像〕→ **接受,降级注释**

红方对。已把注释从"mirrors the RTL closely enough"改为明确标注**"SIMPLIFIED model, NOT a faithful RTL mirror"**,列明缺失项(只检 RE-sync 相位、无 FEsync/isREsync、无 elemCount、无 128-bit 帧组装),并写明"do not use it to certify RTL correctness"。它只用于粗略字节序实验。

## BUG-3〔branch 只数个数、目标地址没解〕→ **接受,字段明确标注 count-only**

红方对——branch packet 的目标地址确实没解(ETM3.5 Thumb 地址压缩 + 异常信息字节复杂,贸然实现易错)。处置:
- `FlowEvent` 加 `addr_is_target` 字段:仅 isync 为 True(真绝对 PC);atoms/branch 为 False。
- branch 的 `addr` 字段注释明确"NOT the branch TARGET, only the prevailing base"。
- CLI 输出 branch 标注 **"(count-only)"**。
- 没有把 branch/atoms 当"还原执行链路"的可信信息(只 I-sync 是)。

## GAP-1〔820 帧 vs 0 帧矛盾未闭合〕→ **接受,已给机制解释(不再用"巧合")**

红方对,"巧合"二字草率。**机制查清**:
- TPIUSync 是"**锁一次 0x7FFFFFFF 后自由跑、每 16 字节吐一帧**"。老 `trace_etm.bin` 有 30 个 `0xFFFFFF7F`(多为 idle/数据里的偶发),**第一个一锁,后面 16KB 全程每 16 字节硬吐一帧 → 820 帧**,内容大多是 idle/垃圾,不是 820 个有效 formatter 帧。
- 新 `raw_nibbles.bin` **一个 `0xFFFFFF7F` 都没有 → 从不锁 → 0 帧**。
- **所以"帧数"根本不是 formatter 存在与否的指标**——单次(可能偶发)锁 + 自由跑就能造出几百帧。正确指标是**周期性 `0xFFFFFF7F`**,两份都没有。
- 结论不变("不发 formatter 帧"),但地基从"巧合"换成"TPIUSync free-run 语义 + 无周期全同步"。

## GAP-2〔realign 评分易被噪声满足〕→ **部分接受**

红方对,`min_run=3` 偏低。已知边界(文档 11 已标 realign 流仅指示性);本轮把 CLI 对外指标改为**只报 I-sync 锚点数**(真值),realign events 标为诊断量(见 GAP-4)。`min_run` 提高 + "run 内须含 flash I-sync"作为后续增强(未做,记入待办)。

## GAP-3〔addr2line 解析成功 ≠ 真执行〕→ **接受,已加源码行过滤**

见 BUG-1 第 3 点:已要求 addr2line 命中**真实源码行**(非 `??:?`)才采信,丢弃纯落段噪声。

## GAP-4〔"3x 提升"指标误导〕→ **接受,对外只报锚点数**

红方对。CLI 现在:I-sync 锚点数是主指标(真值),exec-atoms/branches 标 **"(count-only)"**,realign events 仅在 `--realign` 时显示并标为诊断。文档 11 的"3.3×"明确是事件计数膨胀、非信息量。

## 重测结果(收紧后)

`etm_decode_cli.py`(默认严格)对 capGND/capDIV16/trace_e2e:
- 锚点范围收紧到 ELF .text `[0x08000000,0x08055d58)`;
- 丢弃 3 个无源码行锚点;
- **18 个真函数全部带 file:line**(HAL_Update / lv_timer_handler / draw_x_ticks / lv_theme_default_init / meter2_timer_cb ...)。

测试:70 用例(+7),etm35lib 98% 行覆盖;上游 amaranth 20 用例绿。

> 一句话:r14 五条全接受。BUG-1 经实测证实之前锚点含假阳性(3→2),已用 Jazelle/AltISA=0 + ELF .text 实际范围 + addr2line 源码行三重收紧;BUG-3 branch 明确标 count-only;GAP-1 的"820 vs 0"用 TPIUSync free-run 语义闭合(帧数非 formatter 指标)。
