## 一句话裁决

> **阶段 0-3 的采集侧数据（0 字节错、CRC 全对、单变量纪律）基本可信且做得干净；但支撑全案的两个核心归因都不成立**：(1)"字节错 0.000% ⇒ 采集无误 ⇒ 走偏是纯解码盲推"——**证伪**，因为字节错判据（RESERVED/BAD_SEQ）在结构上**测不出"漏地址锚点但仍合法"这类采集损失**，蓝方拿一个盲区当证明；(2)"追平满血 480M"——**算账证伪**，BB=1 在 150M 就溢出，480M 全 BB 生成率 ≈ 已溢出量的 3.2×，BB-OFF 省 6× 后在 480M 仍 > 112.5M 端口，**目标在 112.5M 端口 + 60KB one-shot 下不可达**。方向裁决：**停止追"满血无损"，改做"函数级采样式剖析"的诚实定位**；下一步唯一该做的实验是**用可复现激励区分"解码盲推" vs "采集漏锚点"**，不是急着上 (a)-(d) 任何一个治标手段。**

## 一、阶段 0-3 逐条判定

### 阶段 0（换 CoreMark，150M/-O0/BB=1）：CRC 全对、11 函数、0 字节错
**判定：成立（采集侧）。** CRC 三算法全匹配官方值证明 CPU 计算正确；0 字节错 + 11 个 CoreMark 函数解出，说明 112.5M 采集前端在这个负载下确实干净。单变量纪律遵守（只换 workload）。
**存疑（非阻断）**：把 CoreMark 改成无限循环让 ETM 持续出流——这改变了 workload 的稳态/收尾行为，后续"覆盖率"统计要注意别把无限循环的重复访问当成"覆盖完整"。

### 阶段 1（只开 -O3）：-O3 比 -O0 慢（228 vs 486），0 字节错
**判定：成立，且归因正确。** "无 cache + flash 等待 → -O3 内联/展开假设有 cache 反被拖慢"与 proposal 29 的 M7-靠-cache 理论自洽，且阶段 3 开 cache 后 2.67× 跃升反证了这条。DWT 硬测 150.1M 排除了时钟异常。单变量守住。
**这条是本次复盘里最扎实的一段。**

### 阶段 2（只开 BB-OFF）：字节率降 ~6×，调用图"仍完整正确"，0 字节错
**判定：部分成立，"调用图完整正确"存疑（被阶段 3 自己推翻）。**
- 字节率 deframed 16313→2760（~6×）可信，这是 BB-OFF 的预期物理效果。
- **但"调用图仍完整正确"是在 no-cache 下测的**，阶段 3 一开 cache 就出现大量假调用。所以阶段 2 的"正确"是**低锚点间距下的侥幸**，不是 BB-OFF 本身可靠。蓝方在阶段 2 就写下"调用图完整"，是**把一个条件成立的结果当成普适结论**——该项目反复栽的老毛病（见 r25/r26/r27）。

### 阶段 3（只开 cache）：分数 2.67×，揭出两个硬约束
**判定：分数跃升成立；两个硬约束的存在成立；但"走偏=纯解码盲推、非采集错"的归因证伪（见 R1）。**
- 2.67× 跃升 + CRC 全对：可信，坐实 cache 价值。
- 约束 2（BB=1+cache 在 150M 就 ETF 溢出 37-64 次）：**方向上成立**（与 proposal 29 一致），但**溢出计数的测法本身有缺陷**（见 R2），"37-64 次"这个数不能用于任何定量外推。
- 约束 1（BB-OFF+cache 假调用）：**现象成立**（`core_list_init→HAL_UART_Init` 在 ELF 里不存在，确是假调用），**但归因不成立**（R1）。

## 二、核心质疑逐条（红方主攻）

### R1 🟥 证伪 —"字节错 0.000% ⇒ 不是采集问题"是拿盲区当证明

**这是全案最关键的方法论错误。**

**证据（解码链源码）**：`opencsd_etm4_run.py` 的字节错判据 = `RESERVED`（非法包头，`STRICT_RESERVED` 集合）+ `BAD_SEQ`。而 ETMv4 的 **Atom 包头是整个 `0xC0-0xFF` 区间**（源码 `ATOM_HDRS = frozenset(range(0xC0,0x100))`），地址包、Trace-Info 等也各有合法编码空间。

**推断（强）**：BB-OFF 流里，采集若**丢掉或串改了一个间接分支的地址包字节、或吞掉一个 Atom**，结果极可能是**另一个仍然合法的包**——它不会落进 `STRICT_RESERVED`，于是 `RESERVED=0` 照旧成立，但解码起点已经错了。**"0 字节错"只证明"没有非法包头"，完全不证明"没有丢/错采集导致的合法但错误的流"。** 这正是稀疏 BB-OFF 流最危险的失效模式：锚点少，丢一个地址包 = 后面一整段盲推起点全错，且无非法包报警。

**所以蓝方的论证链**"字节错 0 + BB=1 干净 ⇒ 走偏纯粹是解码盲推"**有一个未验证的跳步**：BB=1 干净只说明"锚点密集时对"，不能反推"BB-OFF 稀疏时采集没丢锚点"——**两个配置的采集应力完全不同**（BB-OFF 流稀疏、间接分支地址包是唯一救命锚点，丢一个的后果远严重于 BB=1 的地址包冗余流）。

**判定：归因证伪（不是"错"，是"未被证明，且用了一个测不出该故障的判据来宣称已排除"）。**

**区分实验（root，下一步唯一优先级）——如何分离"解码盲推误差" vs "采集漏锚点"**：
1. **同一段 BB-OFF 抓样，抓两份**：一份走当前 one-shot；关键是**在 FPGA 侧同时并存一份 BB=1 的地址包冗余**做交叉。做法：
   - **实验 1（决定性、纯软件、零上板）**：把**同一个 BB-OFF 字节流喂两遍 OpenCSD**，一遍正常解、一遍在每个间接分支地址处**用 ELF 强制校正 PC**（`opencsd_etm4_run` 已有 ELF）。若"假调用"在强制校正后消失 → 是盲推误差；若强制校正后**间接分支目标地址本身就不在 ELF 的合法 BL/BLX 目标集** → 是采集把地址包采错了（采集问题）。
   - **实验 2（采集完整性直测）**：BB-OFF + cache 下，**同时**读 ETF 的 `TRCSTATR`/formatter 计数 或 在 FPGA 侧统计 A-sync 间的字节数分布。若某些 A-sync 区间字节数**系统性偏少**（vs BB-OFF no-cache 的同区间），说明高速下采集在丢字节（漏边沿类，见 r27）。
   - **实验 3（黄金对照）**：用 **BB=1 + cache + 降 TRACECLK 到不溢出的低 CPU 频**（比如 CPU 降到 50-80M 让 BB=1 不爆），此时既有密集锚点又无溢出，解出的调用图作为**该 workload 的 ground truth 调用序**；再把 BB-OFF+cache 的结果与它 diff。假调用若在 BB-OFF 独有 → 盲推；若两者都有 → 采集/解码共性问题。
2. **判据**：假调用的目标地址是否落在 ELF 的合法调用目标集内。落在（只是路径选错）= 盲推；不落在（目标地址本身是脏的）= 采集。

**在做完这个区分之前，(a)-(d) 任何方向都是盲目下注。**

### R2 🟨 存疑（测法不可信）— 带宽/溢出测量无法量化"真实生成率 vs drain"

**证据（proposal 36 §4.1 + 阶段 3 约束 2）**：蓝方从 one-shot 抓样"有效数据占比 × TRACECLK"估生成率，用 ETF Overflow 计数判溢出。

**推断（强）**：抓样字节率被端口速率**钳制在 ≤112.5MB/s**（每 TRACECLK 周期最多 1 字节）。**一旦 ETM 生成率 > 端口 drain，你在 FPGA 端看到的永远是 112.5MB/s 封顶 + ETF 溢出标记，无法测出"真实生成率到底是 130 还是 250MB/s"。** 蓝方自己在约束 2 里也写"抓样有效数据占比 ~50%（端口限制后的值，真实生成率更高）"——**即承认这个测法测不到真值**，那"150M 就爆"只能定性（确实爆了），**不能定量外推到 480M**（不知道爆多少）。

**判定：溢出"是否发生"的结论成立（Overflow 计数 > 0 是硬事实）；但"生成率数值"和任何基于它的外推都不可信。**

**如何真正量化生成率 vs drain（root）**：
- **停核积分法**：`TRCSTALL` 停核 + ETF 设为 circular buffer 模式，让 CPU 跑固定 N 条指令后 halt，读 ETF 里累计的字节数 → 得到"N 指令产生多少 trace 字节"的**无钳制真值**（因为停核时 drain 不再是瓶颈）。除以 N/CPU频率 = 真实生成率 MB/s。这是唯一能测超过端口上限的生成率的办法。
- 有了真值才能算 480M 的账（见 R3）。

---

### R3 🟥 证伪 —"追平满血 480M"在 112.5M 端口 + 60KB one-shot 下不可达（算账）

**算账（基于蓝方自己的实测 + proposal 29 机制）**：

1. **BB=1 @150M CPU 已溢出**（ETF Overflow 37-64）。即 150M 全 BB 生成率 **已 > 112.5MB/s**。设 150M 全 BB 生成率 = G₁₅₀ > 112.5。
2. **生成率≈正比于 CPU 指令吞吐**（proposal 29：分支率 ∝ 指令率 ∝ 主频，cache 命中下近线性）。480M / 150M = **3.2×**。故 G₄₈₀(BB=1) ≈ 3.2 × G₁₅₀ **> 360 MB/s**。
3. **BB-OFF 省 ~6×**（阶段 2 实测 deframed 16313→2760）。但注意这个 6× 是 **-O3 no-cache** 下测的；cache 全速下间接分支/返回的**绝对速率**随主频线性涨，6× 是比例不是绝对下限。
4. G₄₈₀(BB-OFF) ≈ G₄₈₀(BB=1) / 6 ≈ **360 / 6 = 60 MB/s** —— **表面上 < 112.5，好像可行**。
5. **但这是均值。** proposal 29 的溢出机制是**峰值**问题（指令 FIFO 64B + ATB 1 字节/周期）：CoreMark 的 `core_list_find`/`matrix` 深循环里间接分支/返回会**成簇爆发**，峰值生成率远高于均值。60KB one-shot 缓冲 @ 60MB/s 均值 = **1ms 窗口**，覆盖不了 CoreMark 一轮（数十 ms），且峰值簇仍可能瞬时超 112.5 触发 ETF(4KB) 溢出。
6. **结论**：480M + BB-OFF 的**均值**也许勉强进端口，但 (a) **峰值仍会溢出**（4KB ETF 挡不住 M7 双发射簇发），(b) **one-shot 只能采样 1ms 片段**，(c) 若再叠 range filter 压均值，就已经不是"全函数进出"而是"部分函数采样"了。

**判定：证伪。**"满血 480M + 全函数进出 + 无损 + 追平"这个复合目标在 112.5M 端口 + 60KB one-shot 下**不可达**。可达的是其真子集之一：{满血负载, 函数级, **采样式**(非连续), 或 **range-filtered**(非全函数)}。

**诚实标注**：若把"追平"重定义为"满血负载下、对**选定热点函数**、**采样式**重建调用时间线"，则可达——但这需要蓝方明确承认边界收缩（见 R6）。

### R4 🟨 成立（补刀）— 阶段 2"调用图完整"与阶段 3"cache 后走偏"暴露单变量纪律的一个隐藏耦合

**证据**：阶段 2（BB-OFF, no-cache）判定"调用图完整正确"；阶段 3（+cache）立刻假调用。

**推断**：蓝方的单变量链把 "BB-OFF" 和 "cache" 分成两阶段，形式上守纪律。但**BB-OFF 的可靠性本身依赖锚点间距，而锚点间距由 cache 决定**——这两个变量**不是独立的**，是**交互项**。阶段 2 单独测 BB-OFF 得到"完整"，给了一个**虚假的绿灯**，掩盖了"BB-OFF 在目标态（cache 开）下不可靠"。

**判定：单变量纪律在形式上遵守，但对存在强交互的两个变量，逐个单独验证会产生"每步都绿、组合起来红"的假象。** 这不是纪律被破坏，是纪律对交互项的固有盲区。教训：**验收必须在目标组合态（cache+BB-OFF+高频）下做，不能靠"每个单变量都绿"推断组合绿。**

---

### R5 🟩 存疑（次要）—"函数进出 = 间接分支+返回"的 ETM 语义不完整

**证据**：proposal §1.2 把"函数进出"等价于 BL/BLX/BX LR/POP PC。

**推断**：BB-OFF 下 **直接 BL（最常见的函数调用）不发地址**，靠 ELF 推断。所以 BB-OFF **恰恰不直接给"函数进出事件"**，而是给"间接分支 + 返回"，直接调用要靠推断填。CoreMark 里 `core_bench_list` 的比较回调是函数指针（间接，OK），但大量 kernel 调用是直接 BL（靠推断）。**一旦推断因锚点稀疏出错（R1 的假调用），"函数进出"就是错的。** 所以 §1.2 的等价关系在 BB-OFF 下不成立——BB-OFF 给的是"间接分支进出 + 直接调用的盲推"。

**判定：概念存疑，非阻断，但影响"函数级 trace"的定义诚实性。**

## 三、候选方向 (a)-(d) 批判与排序

**先说结论：(a)(b)(c)(d) 全是治标，且在 R1 未解决前都是盲目下注。** 但若强制排序：

| 方向 | 批判 | 是否治标 | 排序 |
|------|------|:---:|:---:|
| (b) BB-OFF + address-range filter 只 trace 关心区间 | **相对最实在**：缩短盲推跨度直接对症 R1 的"锚点间距过大"，且 range filter 是 ETMv4 硬件原生能力。**但**它把"全函数进出"降级为"选定区间函数"——是**边界收缩**，应诚实叫"热点采样"而非"追平" | 治标但方向对 | **1** |
| (a) BB-OFF + 提高 TRCSYNCPR 加密 A-sync | A-sync 是**周期性全同步锚点**，能定期把盲推拉回，直接补偿 R1 的盲推漂移。**但**加密 A-sync 增加字节率（与降带宽目标矛盾），且 A-sync 只在周期边界纠正，簇发的错误调用在两个 A-sync 之间仍错 | 治标 | **2** |
| (c) 降 CPU 主频找 BB=1 不溢出临界 | **诚实但放弃目标**：BB=1 准，降频到不溢出能得 ground truth，**对 R1 的区分实验(实验3)有用**。但"离满血远"= 直接放弃"追平"。作为**诊断手段**有价值，作为**方案**是投降 | 诊断有用/非方案 | **3（仅作诊断）** |
| (d) TRCSTALL 停核无损 | **改变时序**（停核 = CoreMark 分数失真），与"满血实时"根本矛盾。但**对 R2 的生成率真值测量极有用**（停核积分法）。作为方案不可接受（侵入），作为**测量工具**必需 | 侵入/非方案 | **4（仅作测量）** |

**蓝方漏掉的根本方向**：
1. **承认定位 = "函数级采样剖析"而非"全程无损追平"**（最重要）。112.5M 端口 + 4KB ETF + 60KB one-shot 的**诚实能力上限**就是"满血负载下对热点函数采样式重建"。这不丢人，是物理约束下的正确定位。r25/r27 一路批的就是"虚荣指标/偷换概念"，这里"追平满血"就是又一次偷换（函数级采样 vs 全指令无损）。
2. **one-shot → 实时流式**（proposal 36 §5 阶段 5 已列，但被排到最后）。**若真要覆盖完整 CoreMark 轮次，流式是唯一出路**，且 FPGA 侧 deframe 去 HSYNC 能把有效带宽利用率大幅提升（BB-OFF 后 non-HSYNC 仅 6.7%，去 HSYNC 后净荷远低于千兆墙）。这比 (a)-(d) 更根本地解决"窗口不足"。
3. **FPGA 侧 deframe/过滤**：把 HSYNC 剥离、只流真 ETM 净荷，等效放大端口有效带宽——对 R3 的带宽账是实质性缓解。

## 四、方法论审查（该项目历史老毛病）

**判定：又犯了，但比 proposal 34 轻。**
- **把未验证假设当结论**：阶段 2"调用图完整正确"（no-cache 下的侥幸当普适）、"字节错 0 ⇒ 采集无误"（用测不出该故障的判据宣称排除）——**重犯**。这正是 r25(proposal 34)、r26、r27 反复指出的模式。
- **单变量纪律**：形式上守得不错（每阶段确实只改一个），是本项目做得好的地方。但对 BB-OFF×cache 这种**交互项**暴露了盲区（R4）。
- **偷换概念**："追平满血"从"全指令无损"悄悄滑向"函数级"，proposal §5 阶段 6 虽自己划了"不声称全指令无损"的边界（这点诚实，值得肯定），但标题和 §0 目标仍写"追平满血 480M"，**标题党与正文边界不一致**。
- **诚实标注做得好的地方**：§4.2 明确标了带宽估算"不确定性大，必须实测"、§8 自设质疑点——这是相比 proposal 34 的进步，应保持。

## 五、下一步明确裁决

### 做什么（P0，全部在花任何 FPGA 综合/上板前）
1. **R1 区分实验（唯一最高优先级）**：跑实验 1（同一 BB-OFF 流喂 OpenCSD，间接分支处用 ELF 强制校正 PC）+ 实验 3（BB=1 降频得 ground truth 调用序）。**判据**：假调用目标地址是否落在 ELF 合法 BL/BLX 目标集内。落在=盲推（则 (b)/(a) 有意义）；不落在=采集丢锚点（则先修采集，(a)-(d) 全部无效）。
2. **R2 生成率真值**：用 TRCSTALL 停核积分法测 150M BB=1 和 BB-OFF 的**无钳制生成率 MB/s**。**判据**：得到 G₁₅₀ 真值，外推 G₄₈₀ = 3.2×G₁₅₀，与 112.5 端口对比。

### 不做什么
- **不要**在 R1 未定性前上 (a)/(b)/(c)/(d) 任何一个——那是对未知根因下注。
- **不要**继续用"字节错 0.000%"作为"采集无误"的验收判据——它是盲区，改用"间接分支目标地址 ∈ ELF 合法目标集"+"A-sync 间字节数分布无系统性缺失"。
- **不要**在标题/目标里保留"追平满血 480M"直到 R3 的账被真值数据推翻或证实。

### 判据（决定方向的分叉）
- **若 R1 = 盲推误差**（采集干净，只是 ELF 推断在稀疏锚点走错）：方向 = **(b) range filter 缩盲推跨度 + (a) 加密 A-sync**，并把目标诚实改为"热点函数采样级剖析"。
- **若 R1 = 采集丢锚点**（高速下漏地址包/漏边沿，回到 r27 的采样完整性问题）：**先修采集前端**（这是 r27 未结的账），(a)-(d) 全部搁置。
- **若 R3 真值确认 G₄₈₀(BB-OFF) 峰值 > 112.5**（几乎必然）：**正式放弃"全程无损追平"**，转 **one-shot 采样式** 或 **实时流式 + FPGA 去 HSYNC**，并把方案标题改为"满血负载下函数级采样剖析"。

## 一句话给用户

**阶段 0-3 采集侧数据是干净的，-O3 反慢和 cache 2.67× 也扎实；但两个撑全案的结论塌了：一是"0 字节错所以采集没问题"——字节错判据只查非法包头，查不出"丢了间接分支地址锚点但流仍合法"这种最致命的采集损失，所以 cache 后的假调用到底是解码盲推还是采集丢锚点，现在根本没被区分开，这是下一步唯一该做的实验（同一流喂 OpenCSD 看假调用目标地址在不在 ELF 合法目标集里，零上板）；二是"追平满血 480M"——BB=1 在 150M 就溢出，480M 全 BB 是它的 3.2 倍，BB-OFF 省 6 倍后均值也许勉强进端口但峰值簇仍爆、且 60KB one-shot 只能采 1ms，一轮 CoreMark 几十 ms，物理上就不可达。(a)-(d) 四个候选全是治标，在没区分清盲推 vs 丢锚点之前上任何一个都是盲赌。诚实的定位是"满血负载下对热点函数采样式剖析"，不是"全程无损追平"——这跟 proposal 34 的"14/14 虚荣指标"是同一类偷换概念，改了标题、用对判据，这个方案才站得住。**
