## 一句话裁决

**"disposition 错位一位"是从单点（a2f2）+ 一条"无条件返回不可能 not-taken"的教科书原则倒推出来的推断，不是逐-atom 对齐实测。** 蓝方连自己都在 p43 §2 标了"H43 仍是假设"、§4 P0"必须先坐实"——那就别把它写进 §1"已坐实的事实"。更要命的是 §1 第 5 条"读到 disp bit=0 → atom 流错位一位"和 r33 §3.5"真实执行流在 HAL 返回后可能并不线性经过 a2f0/a2f2"是**两个互相矛盾的机制**：前者说"位错了一格"，后者说"指令序列本身走错了（不是错位是错路）"。两个机制指向完全不同的修复，蓝方没区分就跳到"修错位"。**方案 A 现在绝不能动 atom 核心（A3）**；A1 与已回滚的 A2 是同一类"落字面量池就当返回"的启发式，**必然同样误伤真实条件分支**（A2 掉 77 cardinality 就是铁证）。fix B 是当前诚实终点，cm_benchmark_main 133 假重入应作为**已知显示噪声接受**，不值得拿全局 68798 条调用边冒险。

## 逐条拷问

### Q1 "disposition 错位一位" —— 🟥 **推断，非实测；且措辞自相矛盾**

**实测部分**（r33 §3.4，可信）：`INSTR@a2f2 ic=1(JUMP) insExec=0 disp&1=0 disp=a` —— 这是真 log，a2f2 处 pop 确实被判 not-taken，workingAddr 越过进字面量池。**这一步是实测，🟩。**

**推断部分**（不可信）："读到 bit0=0 → atom 流与指令流错位一位"。这是**从"pop{pc} 无条件、ETM4 语义 atom 必为 E"这条原则反推**的。问题：

1. **只看了 a2f2 一个点**。"错位一位"是个**关于整段 atom 序列相位**的断言，但蓝方没有把 HAL 返回后这批 `disp=0xa` 的每一位逐个对到真实执行的分支序列、证明"整段恰好偏移一格且偏移量恒为 1"。看一个点判"错位一位"，和 p42 §2.5 看 a2f2 一个点判"pop 分类失败"是**同一个方法论错误**——只是这次分类那步（loadelf）被证伪了，换了个"错位"的说法接着单点推断。

2. **"错位一位" vs "错路" 自相矛盾**（关键）：
   - p43 §1.5 / r33 §3.4：**disposition 位流错位一位**（bit 对错了指令）。
   - r33 §3.5 / p43 §2 H43：**"真实执行流在 HAL 返回后可能并不线性经过 a2f0/a2f2"**（即指令序列本身不该走 a2f0→a2f2，是推测返回把 workingAddr 设错了地方）。
   - **这两个不是一回事**。前者：指令序列对、bit 数组偏移 1。后者：bit 数组对、指令游标 workingAddr 起点错（推测返回设成 a2f0 但真实不在这）。**修复方向完全相反**——前者要移 disposition 指针，后者要修 stacked-candidate 的 workingAddr 锚定。蓝方把两个混着写，说明**根因根本没定死**。

**判定 🟥**：核心断言"错位一位"是推断，且与自己的另一处描述矛盾。**这是 p42→r32→r33 一路"没坐实就命名根因"的第三次复发**，只是这次名字叫"disposition 错位"。

---

### Q2 stacked-candidate 返回的 atom 指针 —— 🟥 **未证；"批次边界" vs "错位"未区分**

r34 提示词自己点出的关键：HAL 返回（committed=false）消耗一个 atom + `disposition>>=1`，推测返回后从 a2f0 线性重走。**a2f2 取的 disp 位到底是不是本该属于 a2f2 的？**

核对代码（mortrall.hpp:625-633）：`disposition >>= 1; incAddr--` 只在 `(protocol!=ETM4) || (ic & LE_IC_JUMP) || SYNC_BARRIER` 时执行。所以：
- HAL 的 `bl`（LE_IC_CALL 含 LE_IC_JUMP）消耗一位。✓
- a2f0 `add sp,#8`（非 jump）**不消耗**。✓
- a2f2 `pop{pc}`（LE_IC_JUMP）消耗下一位。

**问题**：HAL 返回是 iBR（committed=false 推测路径）。iBR 返回分支（662-679）里**没有 `disposition >>= 1`**——它在进入 `while(incAddr)` 循环体内、`insExecuted` 判定**之后**走 CALL/JUMP 分支才移位。那么 HAL 返回那一步到底有没有消耗 atom？如果 HAL 的 `bl` 已经消耗了它自己那位，而返回是"下一批 atom 的事"，则 a2f2 取的可能是**新一批的 bit0**——这不是"错位一位"，是**批次边界**（一个 EV_CH_ATOMS 批次结束、下一批开始时 workingAddr 停在哪）。

**蓝方从未证明是"错位"而非"批次边界"**。这俩的区别：
- 错位：同一批 disposition 内部 bit 与指令错开 → 修 disposition 消费逻辑。
- 批次边界：两个 EV_CH_ATOMS 之间 workingAddr 推进与 atom 补给不同步 → 修批次衔接（可能是 stacked-candidate 未 commit 时提前消费了下一批的位）。

**判定 🟥**：Q2 是 proposal 的命门。P0 必须首先区分这两者，否则 A1/A2/A3 全是打在错误假设上。

### Q3 opencsd 参照矛盾 —— 🟥 **参照失效未解决，却写进 P0 当基准**

p43 §7 / r33 自认："opencsd lister 地址只到 0x80094dc、没有 0x800a2xx，但覆盖统计 cm_benchmark_main=27"。

**这是硬矛盾**：
- 若 opencsd **没解码** 0x800a2xx（cm_uart 区），那它凭什么统计出 cm_benchmark_main=27？说明 lister dump **被截断**了，不是 opencsd 没走到。
- 若 opencsd **解码了** 0x800a2xx 但 lister 只显示到 0x80094dc，那 lister 的地址范围是**输出过滤/截断**造成的，不能当"opencsd 执行路径不同"的证据。

**两种可能蓝方都没查清**，却在 §4 P0 里写"交叉 opencsd 的 atom 消耗序列作参照"。**参照基准自己都没验证可用性**。而且更根本：opencsd 和 mortrall 是**两个独立 ETMv4 解码器实现**，opencsd 覆盖统计里 cm_benchmark_main=27 vs mortrall 发 133 begin——**这 27 vs 133 的差本身就是最强的对齐线索，但蓝方没去解释这个数字**。27 接近真值区间（CoreMark 一个 slice 里的真实迭代数），133 是 mortrall 的假重入——**opencsd 27 说明它没有这个 bug**，那 P0 就该直接 diff "opencsd 在 0x800a2f2 处消耗第几个 atom / 判 taken 还是 not-taken" vs mortrall，而不是纠结 lister 地址范围。

**判定 🟥**：opencsd 参照能不能用，是 P0 能否成立的前提，现在**未解决**。必须先把 lister 截断问题查清（大概率是 dump 参数截断，opencsd 其实解码了全程）。

### Q4 A1/A2 "落字面量池就当返回"必然误伤 —— 🟩 **成立（A2 已用实测证明）**

**这条我完全同意蓝方的自我否定，且 A1 有同样的坑。**

A2 判据"fall-through 无源码行映射（`symbolLineAt==NULL`）→ 判返回"，实测掉 77 cardinality。机制清楚：
- **真实条件间接分支** not-taken 时，fall-through 落在**函数尾部/对齐填充/字面量池边界**是**合法且常见**的（编译器把 `.word` 池紧贴代码放）。
- IT 块内 `popcc {pc}`、`tbb/tbh` 跳转表、条件 `ldr pc` —— 这些 not-taken 的 fall-through 都可能命中无行映射区。A2 把它们全误判成返回 → 弹栈 → 丢真实 PC → cardinality -77。

**A1（p43 §3）判据"下一线性地址落在字面量池/数据区（symbolFunctionAt 找不到指令）"——这和 A2 是同一类信号**，只是 A1 用 `symbolFunctionAt==NULL`、A2 用 `symbolLineAt==NULL`。两者对"真实条件分支 fall-through 到边界"的误判率几乎一样。**A1 必然重蹈 A2 覆辙**，掉 cardinality。

**判定 🟩**：Q4 成立。A1 不用试都能预判失败——它和 A2 是同一个启发式的两个变体。**这正是"没坐实机制就试启发式"的典型：不知道为什么判 not-taken，就在"判错之后的症状"（走进数据）上打补丁，必然误伤合法的"走进数据"场景。**

### Q5 该不该动 atom 核心（A3）—— 🟥 **坚决不动**

**收益**：cm_benchmark_main 133→1（假设成功）。**视觉**：Perfetto 里 cm_benchmark_main 多出 132 个假 begin。但 coremark_main 已被 fix B 从 358 压到 7——**主可视化问题已解决**，cm_benchmark_main 是次层噪声。

**风险**：A3 改 stacked-candidate 的 atom 对齐，直接动 `while(incAddr)` + `disposition` + `incAddr` 循环核心。这是：
- r32/r33 反复标注的雷区；
- 全局 68798 条调用边（verify_calls 对 ELF）的生命线所在；
- **且在根因（Q1/Q2）都没定死的情况下动核心 = 拿 68798 条边赌一个未证假设**。

**判定 🟥**：绝不动 A3。ROI 极负——为消 132 个次层假 begin，赌上全局解码正确性，而且修的可能是错的机制（Q1 矛盾、Q2 批次边界未排除）。**fix B 是可接受的工程终点。**

### Q6 P0 怎么设计才能真正坐实 —— 见下方 P0 清单

蓝方 §4 P0 的问题："逐-atom dump 确认错位一位"——**预设了结论是"错位一位"**，然后去"确认"。这是**验证性偏误**（confirmation bias）的设计，不是可证伪实验。正确的 P0 必须能**区分四个互斥假设**并让数据自己选（见下）。

### Q7 丢包干扰 —— 🟥 **从未在零丢包抓样验证过；且 fixture 里根本没有零丢包切片**

**实测核查**：`captures/mortrall_fixture/` 里只有 `slice.aligned.bin`(4MB) 和 `slice2.aligned.bin`(8MB)，**两个都来自同一份 0.1% 丢包的 986MB 抓样**（r33 §4 明说 slice2 是"986MB 抓样里另一段 skip 200MB"）。**fixture 里不存在零丢包参照。**

蓝方的"91/91 HAL 返回都触发、丢包做不到 91/91"论证（r33 §4）：
- **只证明了"这个失效是系统性的、不是随机丢包"**——这点我接受 🟩（91/91 确定性对应，丢包是随机的，做不到）。
- **但没排除"系统性失效的成因本身包含丢包导致的固定错位"**。0.1% 丢包 = 965/964298 帧。如果某个固定位置的丢包**每次 CoreMark UART 打印时都落在同一相对位置**（因为 UART 打印是周期性的、丢包也可能与某周期性事件相关），就能造出"看似系统性、实则丢包驱动"的 91/91。蓝方的论证排除了"随机丢包"，**没排除"周期性/结构性丢包"**。

**更根本**：两个 slice 同源同丢包率，**"独立验证"是假独立**——它们共享同一个丢包 pattern。r33 §7 说"slice2 证明 B 不是过拟合 slice1"，但 slice2 和 slice1 是同一次抓样的两段，**丢包成因若在采集链，两段都带同样的病**。

**判定 🟥**：H43 从未在零丢包抓样验证。这是**必须先补的 P0**——在坐实"错位机制"之前，先证明这个现象在零丢包数据上依然存在。若零丢包下现象消失或大变 → 根本不是解码器 bug，是采集/对齐问题，proposal 43 整个作废。

## P0 清单（动手前必须跑，按优先级；每条都可证伪、判据明确）

### P0-1 🔴 最高优先 — 零丢包抓样复现（先排除 Q7）
- **做法**：抓一份**零丢包**的 CoreMark slice（`stream_lost_cnt==0` + UDP `seq-gap==0` 全程，抓短一点无所谓，只要覆盖几轮 UART 打印）。跑同一 mortrall + regress.py。
- **判据**：
  - cm_benchmark_main 假重入率（假 begin / 真 UART 打印轮数）与 0.1% 丢包 slice **相同** → 系统性解码 bug，继续 P0-2。
  - 假重入**消失或显著下降** → 丢包驱动，proposal 43 作废，回去查采集/nibble 对齐。
- **为什么第一**：整个 proposal 建立在"这是系统性解码 bug"上，而唯一的验证数据全是同源丢包切片。这个前提不先钉死，后面全白做。

### P0-2 🔴 opencsd 参照可用性（解决 Q3）
- **做法**：把 opencsd lister 的地址截断问题查清——重跑 `opencsd_etm4_run.py --dump-lister` **不加任何地址过滤**，确认 opencsd 是否解码了 0x800a2f2 区间。
- **判据**：
  - opencsd 覆盖到 0x800a2xx 且能 dump 出该区的 atom 消耗 → 参照可用，进 P0-3。
  - opencsd 确实没走到该区 → 两解码器路径不同，**必须换基准**（手工按 IHI0064 ETM4 spec 对齐这批 atom），P0-3 改用手工基准。
- **附带**：解释 opencsd cm_benchmark_main=27 vs mortrall 133 这个 27 是怎么来的——它是最直接的"opencsd 没这个 bug"证据。

### P0-3 🔴 区分四个互斥假设（解决 Q1/Q2，取代蓝方"确认错位一位"的偏误设计）
- **做法**：在 HAL 返回（committed=false）到 a2f2 pop 这段，逐-atom dump 下列**全部**字段，喂给一个判定表：
  ```
  每个 atom: (EV_CH_ATOMS 批次序号, 批内 index, disposition 原值, incAddr,
             workingAddr, ic, insExecuted, 是否 committed, 栈候选地址)
  ```
- **四假设判据表**：
  | 观测 | 结论 |
  |---|---|
  | 同一批内 disp 位与指令逐个对齐、仅在 a2f2 处 bit=0 且该 bit 本应属于下一条 | **真·错位一位** → A3 的移位方向 |
  | a2f2 取的 bit 属于**新一批** EV_CH_ATOMS，上一批在 HAL 返回处提前耗尽 | **批次边界** → 修 stacked-candidate 不该跨批消费 |
  | workingAddr 在推测返回时被设成 a2f0，但真实下一个地址包指向别处 | **锚定错（错路非错位）** → 修 committed=false 的 workingAddr 来源 |
  | 该段 atom 与 opencsd/spec 基准**逐位一致**、是 mortrall 消费逻辑独有偏差 | **消费逻辑 bug** → 定位到具体消费点 |
- **判据**：四选一必须由数据唯一确定，不允许"看着像错位"。**若数据不能唯一区分 → 说明信息不足，继续加 dump，不动代码。**

### P0-4 🟡 verify_calls 全量基线固化
- 在动任何代码前，把当前 fix B 的 verify_calls（68797/68798）+ cardinality（2646/3038）+ 内层篮子**双 slice 存成 golden**，任何 A 方案改动后逐项 diff。（regress.py 已有，确认它跑双 slice。）

## 明确表态

1. **A3（改 atom 核心）现在绝对不能动。** 根因有两个互相矛盾的版本（错位一位 vs 错路），Q2 的批次边界假设没排除，Q7 的零丢包验证没做。在这三个都没钉死前动核心，是拿全局 68798 条调用边赌一个未证假设——比 A2 掉 77 cardinality 严重一个数量级。

2. **A1 不要试。** 它和已回滚的 A2 是同一个"落数据区就当返回"启发式的变体，必然同样误伤真实条件分支 fall-through，掉 cardinality。试它纯属重复 A2 的错误。

3. **fix B 是当前诚实终点。** coremark_main 358→7、调用边 68797/68798 对 ELF、cardinality 不降——这是可用的工程状态。cm_benchmark_main 133 假重入是**已知次层显示噪声**，应记入 known-issues 接受，不值得为它冒险。

4. **若一定要往下走，唯一正确路径是先跑 P0-1（零丢包复现）→ P0-2（opencsd 参照）→ P0-3（四假设互斥判定）**，用数据唯一确定根因后再谈修复。**在 P0-3 给出唯一结论之前，禁止写任何修复代码**——这是对"没坐实就动手"惯犯的硬约束。
