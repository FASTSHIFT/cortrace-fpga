# r13 · STM32F429 ETM 指令 trace 官方支持核查

> 触发：r12 收口前必须先确认一个前提——**F429 到底支不支持完整指令 trace？** 若硬件根本没这能力，前面所有 ETM 寄存器调试都是徒劳。
> 方法：查 ARM 官方 TRM / 架构规范 + SEGGER / ST 官方与社区一手资料。
> 结论先行：**F429 硬件确定支持完整 4-bit 并行 ETM 指令 trace。能力没问题，问题在使能路径——而权威资料恰好指向 r12 的判断。**

---

## 1. 官方结论：F429 支持完整指令 trace（确凿）

### 1.1 ARM 官方——ETM-M4 就是干这个的

ARM **CoreSight ETM-M4 TRM（DDI0440）** 原文（已改写以符合引用规范）：
- ETM-M4 是一个**可选**调试组件，使调试器能够**重建程序执行流**（[developer.arm.com/docs/ddi0440/c](https://developer.arm.com/docs/ddi0440/c/introduction/about-the-etm-m4)）。
- ETM-M4 **只支持指令 trace**（instruction trace），可配合 Cortex-M4 TPIU 使用，经并行 trace 端口输出。

含义：**只要这颗芯片集成了 ETM-M4（可选项），它给出的就是完整指令流 trace**（分支广播 + 上位机用 ELF 镜像补全顺序指令，这正是 Orbuculum/orbmortem 做的事）。ETM-M4 没有"精简版只给部分"这种档位——要么没集成，要么就是完整指令 trace。

### 1.2 F429 确实集成了 ETM——SEGGER + ST 双向证实

- **SEGGER 知识库 "Tracing on ST STM32F429"**（已改写）：F429 这颗 MCU 通过引脚实现 tracing，因此 J-Trace 可以对它做 trace（[kb.segger.com/Tracing_on_ST_STM32F429](https://kb.segger.com/Tracing_on_ST_STM32F429)）。
- **SEGGER "4-Pin Trace with STM32F429"** 专页：直接提供 Keil µVision + J-Trace 做 **4-pin ETM trace** 的完整配置流程和 `STM32F429.zip` 样例工程（[kb.segger.com/4-Pin_Trace_with_STM32F429](https://kb.segger.com/4-Pin_Trace_with_STM32F429)）。**SEGGER 卖的 J-Trace 把 F429 列为支持机型，等于厂商背书 F429 的 ETM 指令 trace 可用。**
- **ST 自己的 DBGMCU** 设计了 `TRACE_MODE=11`（4-bit 同步）的硬件路径——若无 ETM，ST 不会做这套并行 trace 引脚复用。

→ **能力维度结案：F429 = ETM-M4 + 4-bit TPIU = 完整指令 trace，硬件支持确定无疑。** 蓝方一度怀疑的"部分 F4 的 ETM 精简版能力有限"对 F429 **不成立**。

---

## 2. 关键发现：所有「能跑通」的官方配置，ETM 使能都由 trace 调试器做，不是手写寄存器

这是本次核查最有价值的一条，直接印证 r12 的根因排序。

### 2.1 SEGGER 官方 4-pin trace 流程——用户根本不碰 ETM 寄存器

SEGGER 专页给的 Keil 配置流程（改写）：设好 .ini → 在 Target Driver Setup 的 Trace 页**勾选 Enable + ETM Trace Enable + Trace Port 设成 "Sync Trace Port with 4-bit Data"** → 开 Instruction Trace 窗口即可。

**注意：整个流程里用户不写任何一个 ETM 寄存器**（ETMCR/TEEVR/TECR1 一个都不碰）。**ETM 的使能握手是 J-Trace + Keil DLL 内部完成的。**

### 2.2 ST 社区同症状案例——Keil 的 .ini 也不碰 ETM

ST 社区 "STM32F429I-EVAL ETM Trace not working"（[community.st.com](https://community.st.com/t5/stm32-mcus-products/stm32f429i-eval-etm-trace-not-working/m-p/486340)）一位用户用 **ULINKpro**（真正的 trace 探针，非 HLA），遇到**和蓝方一模一样的症状**：PE2-6 已确认配好、ITM/SWO 能跑、4-bit ETM 报 **"No Synchronization"**，甚至把核降到 16MHz HSI 都不行，且同探针在 LPC1769 上 4-bit ETM 完全正常。

他贴的 Keil `STM32_TP.ini` 初始化文件**只做两件事**：
```c
// 只配 GPIOE（PE2-6 → AF0 / very-high-speed / no-pull）+ DBGMCU
_WDWORD(0x40021000, 0x00002AA0); // GPIOE_MODER: PE2..PE6 = AF mode
_WDWORD(0x40021008, 0x00003FF0); // GPIOE_OSPEEDR: PE2..PE6 = 100MHz
_WDWORD(0x4002100C, 0x00000000); // GPIOE_PUPDR: no pull
_WDWORD(0x40021020, 0x00000000); // GPIOE_AFRL: AF0
_WDWORD(0xE0042004, 0x000000E7); // DBGMCU_CR  ← 和蓝方完全一样的 0xE7
```
**ETM 寄存器（ETMCR/TEEVR/…）一行都没有**——因为 Keil 的 ULINK 驱动会在 trace 使能时自己做 ETM 编程握手。

### 2.3 这两条对蓝方意味着什么

**蓝方走的是 OpenOCD + ST-Link HLA + 手写 ETM 寄存器——这条路在所有官方/成熟方案里都不存在。** 成熟方案里 ETM 的使能是 trace 探针的固件/DLL 干的（J-Trace、ULINKpro），用户只配 GPIO + DBGMCU。

这正面印证 r12 的排序：
- **r12 嫌疑 1/2（运行态配置没生效 / prog 时序没轮询）** ← Keil/J-Link 之所以能成，是它的 DLL 严格做了 prog 进入/退出轮询 + 在正确时机 latch，手写脚本最容易在这里出错；
- **r12 嫌疑 4（HLA 静默丢写 / OpenOCD etm 子系统在 HLA 下不可用）** ← 蓝方自己（提交 `42e872d`）已坐实 OpenOCD 原生 etm 在 HLA 下用不了。official 全都用真 trace 探针（J-Trace/ULINKpro 走全 SWD/JTAG），**没有人用 HLA 手戳 ETM 成功**。

## 3. 一个必须正视的告警：ULINKpro 用户也卡 "No Synchronization"

ST 社区那位用**专业 trace 探针**的用户，规规矩矩用 Keil，**仍然**卡在 F429 4-bit ETM "No Synchronization"。这说明 F429 的 4-bit ETM trace **存在一个超出"寄存器配置"的已知难点**，业界踩过坑。常见根因（按社区/经验）：

1. **TRACECLK 速率 / 信号完整性**：F429 的 TRACECLK 默认可能跑到很高（HCLK 相关），EVAL/DISC 板的 trace 走线 + 探针接法对 4-bit 同步 trace 的 SI 要求高，"No Sync" 常是采样端在高速下锁不住——**但蓝方这一侧反而是强项**（FPGA V1 自环 14-tap 眼、能锁 sync）。
2. **ETM 使能握手**：如上，手写比 DLL 容易漏 prog 轮询/latch 时机。

→ 对蓝方的意义：**SI/采样侧蓝方已经证明健康（能锁 sync），所以蓝方比那位 ULINKpro 用户更接近成功——蓝方唯一缺的就是 ETM 使能握手这一步**，而这正是 r12 嫌疑 1~4 锁定的范围。

## 4. 与 r12 结论的合并裁定

| 问题 | 核查结论 |
|---|---|
| F429 硬件支持完整指令 trace？ | ✅ **支持**（ETM-M4 + 4-bit TPIU，ARM TRM + SEGGER/ST 三方证实）|
| 是"精简 ETM 能力不足"吗？ | ❌ **不是**。ETM-M4 要么没有要么就是完整指令 trace；F429 有 |
| 蓝方"配置全对却 idle"是硬件极限吗？ | ❌ **不是**。是使能路径问题 |
| 成熟方案怎么使能 ETM？ | **trace 探针(J-Trace/ULINKpro) 的 DLL/固件做 ETM 握手；用户只配 GPIO+DBGMCU**。没有"HLA 手写 ETM 寄存器"的成功先例 |
| r12 的根因排序对吗？ | ✅ 印证。尤其嫌疑 1/2（运行态 latch / prog 轮询）和嫌疑 4（HLA 不暴露 trace 子系统）|

## 5. 据此修正下一步建议（接 r12）

r12 给了 8 条单命令检查。结合本核查，**优先级重排**：

1. **【最高】换掉"HLA 手写 ETM"这条本就不存在的路**。两个方向二选一：
   - **(a) 借成熟 DLL 做 ETM 握手**：用 **J-Link**（OB 也行）/ ULINKpro，或 SEGGER 的 `STM32F429.zip` 样例工程跑通一次 official 4-pin ETM trace，**先证明这颗芯片这块板能出真 trace**——把"使能"交给被验证过的实现，自己只接 FPGA 采。这是最快坐实"能不能出指令流"的一刀。
   - **(b) 换出 HLA**：OpenOCD 用 `dapdirect_swd`（新版 ST-Link 固件支持）或 CMSIS-DAP 探针，拿到真 AP 访问后再手写 ETM——但仍要自己复刻 prog 轮询/latch 时序（r12 嫌疑 2）。
2. **若坚持手写**：严格按 r12 嫌疑 1/2 做——清 prog 后**轮询 ETMSR bit1→0**、且 ETM 配置必须在**最后一次 resume 之前**完成并二次 halt 回读验证（戳穿"读回 0x980"的 halted 假象）。
3. **ITM+DWT bisection 仍要做**（r12 §4）：它能一次性确认 TPIU/采样链健康、把故障钉死在 ETM 使能侧。

---

## 6. 一句话结论

**官方资料三方确认：STM32F429 集成 ETM-M4 + 4-bit TPIU，硬件完整支持指令 trace，绝非"精简版能力不足"——SEGGER 直接把 F429 列为 J-Trace 4-pin ETM 支持机型并提供样例工程。关键发现是：所有能跑通的官方方案里，ETM 使能握手都由 trace 探针的 DLL/固件完成，用户只配 GPIO+DBGMCU，从不手写 ETM 寄存器；而蓝方走的"OpenOCD + ST-Link HLA + 手写 ETM"在业界没有成功先例（蓝方自己也已坐实 HLA 不暴露 OpenOCD etm 子系统）。这正面印证 r12 的根因排序——问题不在芯片能力，在使能路径。下一步不是放弃 ETM，而是把使能交给成熟 DLL（J-Link/ULINKpro 或 SEGGER 样例工程跑通一次）或换出 HLA（dapdirect/CMSIS-DAP），FPGA 采样侧已证明健康（能锁 sync），蓝方其实比社区里卡 'No Sync' 的 ULINKpro 用户更接近成功。**
