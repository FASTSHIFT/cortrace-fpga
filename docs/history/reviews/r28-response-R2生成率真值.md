# r28 响应 — R2 生成率真值测量（无钳制 ETM 生成率 vs 端口 drain）

**日期**：2026-07-19
**回应**：r28 红方 R2（one-shot 抓样被端口钳制在 ≤112.5MB/s，测不到真实生成率，"150M 就爆"不能定量外推到 480M）+ R3（"追平满血 480M"可达性算账，缺 G₄₈₀ 真值）
**立场**：接受红方 R2。本文用实测拿到无钳制生成率真值点，线性外推 G₄₈₀，回答 R3 的可达性账。

---

## 0. 方法选择：为什么不用红方建议的"TRCSTALL 停核积分法"

红方 R2 建议用 `TRCSTALL` 停核 + ETF circular buffer 测无钳制生成率。**先做了停核可行性验证，
结论：此 H7 拓扑下 TRCSTALL 不触发，停核法不成立。**

**实测（150M + cache + BB=1）**：
| 配置 | Iterations/Sec |
|------|:---:|
| ETM 关（自由运行基线） | 611.89 |
| ETM 开 BB=1 + **TRCSTALLCTLR=0x10C**（ISTALL+LEVEL max） | **611.89**（完全不变）|

`TRCSTALLCTLR=0x10C` 读回确认已写入，但 CoreMark 分数**一点没降**——CPU 从未被节流。
**根因**：H7 trace 拓扑是 `ETM → CSTF → ETF(4KB) → TPIU`。ETF 溢出时**直接丢帧**
（overflow packet），**不回压到 ETM 的指令 trace FIFO**，所以 `TRCSTALLCTLR` 的
"buffer 低水位停核"条件永不满足。TRCSTALL 只在 ETM 自身 FIFO 满时才停核，而 H7 的瓶颈在
下游 ETF→TPIU 出口，ETM 自身 FIFO 不满。

**副产物结论（回应红方候选方向 (d)）**：**红方候选 (d)"TRCSTALL 停核无损"在此 H7 拓扑
不成立**——它挡不住 ETF→TPIU 出口溢出，停核积分法也测不到 drain。改用频率外推法。

---

## 1. 频率外推法：低频不溢出点测无钳制真值

**原理**：当某频点 BB=1 生成率 < 端口 drain（112.5MB/s）时，ETF 不溢出，
FPGA 抓样的 deframed 净 ETM 字节数 / 真实抓样窗口 = **未被钳制的真实平均生成率**。
cache 命中下生成率随 CPU 频率单调增，取两个不溢出点线性拟合外推到 480M。

**真实窗口修正**：FPGA timebase 读数系统性低估 6.6%（跨会话坐实的恒定比 1.066），
或直接用 drain 上限反算：61440 B one-shot 填满 @ 112.5 MB/s → 真实窗口 =
61440/112.5e6 = **546.1 µs**（两样本 depth 相同，窗口相同）。timebase 读 582.5µs / 1.066
= 546.4µs 一致，互证。

### 实测四频点（BB=1 + cache + O3，TRACECLK 恒 112.5M，同 CoreMark workload）

| sysclk | PLL P | deframed 净 ETM (B) | OVERFLOW 包 | 钳制? | 生成率 = 净/546.1µs |
|:---:|:---:|:---:|:---:|:---:|:---:|
| **50 M** | 9 | 9772 | **0** | 否（真值）| **17.9 MB/s** |
| **75 M** | 6 | 12264 | **0** | 否（真值）| **22.5 MB/s** |
| 112.5 M | 4 | 23887 | 198 | 是（封顶）| — 非真值 |
| 150 M | 3 | 28475 | 183 | 是（封顶）| — 非真值 |

> 溢出计数 = `trc_pkt_lister -decode` 输出里 OVERFLOW 出现次数。50M/75M 严格 0 溢出，
> 是无钳制真值；112.5M/150M 已溢出，其净字节是端口封顶后的残值，**不能当生成率**
> （正是红方 R2 指出的钳制盲区，此处用 0-溢出点回避它）。

## 2. 外推 G₄₈₀ 与 R3 可达性裁决

两个真值点 (50M, 17.9) (75M, 22.5)：

- **线性拟合**（斜率+截距）：k=(22.5−17.9)/(75−50)=0.184 MB/s/MHz，b=8.7
  → **G(480M) = 0.184×480 + 8.7 ≈ 97 MB/s**
- **过原点比例**（保守上界，用 75M 斜率 0.30）：G(480)=0.30×480 ≈ **144 MB/s**
- **过原点比例**（用 50M 斜率 0.358）：G(480)=0.358×480 ≈ **172 MB/s**

**三种模型 G₄₈₀(BB=1) ∈ [97, 172] MB/s。**

**对 R3 的裁决**：
- 若取最乐观的线性拟合 97 MB/s < 112.5 端口 → **均值也许勉强进端口**；
- 但两个比例模型（144/172）都 > 112.5 → **均值就已超端口**；
- **无论哪个模型，都远超红方 R3 算的"BB=1 @480M > 360MB/s"吗？** 否。红方 R3 用
  "150M 已溢出 ⇒ G₁₅₀>112.5 ⇒ ×3.2 = >360" 的外推，**被本实测证伪**：G₁₅₀ 真值其实
  只有 ~33 MB/s（0.184×150+8.7），**远低于 112.5**！150M 溢出**不是因为均值超端口**。

**这推翻了红方 R3 的一个前提，但强化了红方 R3 的最终结论（不可达），换了个机制：**

## 3. 关键发现（比红方 R3 更狠）：溢出是峰值驱动，不是均值驱动

**矛盾点**：
- G(150M) 外推均值 ≈ 33 MB/s，**远低于 112.5 端口**；
- 但 150M BB=1 实测**溢出 183 次**；112.5M 溢出 198 次。
- **均值只有端口的 1/3，却大量溢出** —— 只可能是**峰值簇发**：CoreMark 的
  `core_list_find`/`matrix`/`state` 深循环里分支成簇爆发，瞬时生成率远超 112.5MB/s，
  4KB ETF 缓冲被瞬间填满溢出，簇间空闲又把均值拉回 33MB/s。

**这正面坐实了红方 R3 第 5 点**（"60MB/s 是均值，峰值簇仍爆"）——而且比红方预想的更严重：
**峰值/均值比 > 3.4×**（均值 33 却在 112.5 端口溢出，说明峰值 > 112.5，峰均比 > 3.4）。

**对"追平满血"的最终裁决**：
- **均值账**（红方 R3）：G₄₈₀ 均值 97~172 MB/s，乐观模型勉强、悲观模型超端口；
- **峰值账**（本发现，决定性）：既然 150M 均值 33 就因峰值簇溢出，**480M（3.2× 指令率、
  峰值也 ×3.2）峰值簇必然远超 112.5 端口，ETF 必溢出**。
- **结论：BB=1 @480M 全指令无损 = 不可达，且瓶颈是峰值簇而非平均带宽。** 单纯提均值余量
  （更快端口）解决不了峰值簇，除非 (a) 停核（此拓扑 TRCSTALL 无效，见 §0）或
  (b) 降生成率（BB-OFF/range-filter 削峰）。

## 4. 对方案的影响（R1+R2+R3 合并结论）

| 红方质疑 | 本轮实测裁决 |
|------|------|
| R1 走偏=盲推还是采集 | **盲推**（前文 r28-response-R1）：地址锚点 13/13 干净 + BB=1 干净双证 |
| R2 测不到真实生成率 | **已测**：50M/75M 无钳制真值点，G₄₈₀ 外推 97~172 MB/s |
| R2 建议的 TRCSTALL 停核法 | **此拓扑不成立**：ETF 溢出丢帧不回压，停核不触发；候选 (d) 同时报废 |
| R3 "追平满血不可达" | **确认不可达**，但机制修正：不是均值超端口（G₁₅₀ 均值仅 33），而是**峰值簇溢出**（峰均比 >3.4×）|

**方向裁决（据 R1+R2+R3）**：
1. **正式放弃"全程无损追平满血 480M"** —— 峰值簇物理上灌爆 4KB ETF + 112.5M 端口，
   且此拓扑无停核退路。
2. **BB-OFF 削峰是唯一在片上降峰值的手段**（不发直接分支地址，峰值簇字节数直接砍）。
   R1 已证 BB-OFF 走偏是盲推局限（非采集），故配 **range-filter 缩盲推跨度** 或
   **加密 A-sync** 补锚点，是正确方向。
3. **诚实定位**：改方案标题/§0 目标为 **"满血负载下对热点函数的采样式/range-filtered
   函数级剖析"**，删除"追平满血 480M"的无损承诺。

**下一步**：据此三条改 proposal 36 的 §0 目标与阶段 4-6，然后落地 BB-OFF + range-filter
（红方候选 b）缩短盲推跨度，验证 cache 全速下调用图不再走偏。
