# 红方评审：M核 Trace · 逻辑门开销分析表

> 评审对象：`M核Trace-逻辑门开销分析表.md`
> 立场：红方。本轮专审："这份标了来源等级的'诚实估算'是否真的诚实且站得住，有没有在🟦/🟨/🟥的掩护下夹带乐观，结论'35T 够用'是否真的稳。"

---

## 总评判

**这份估算的"方法论诚实度"高（给区间、标来源、用 20,800 LUT 保守分母、明确只评面积不评时序），值得认可；但它的"结论稳健度"被三件事系统性高估：①占用率分母用了 100% 可用率，未做布线可用率折算；②以太网三块全部偏乐观，且 buffer"转去 BRAM"被当成稳赢；③"只评面积"这个免责被用来回避"时序收敛会膨胀面积"。把这三重压力同时加上，最坏情况会把 35T 推到 ~85–100%+ 可用 LUT——不是"留有余量"，而是"贴边甚至破"。结论应从"35T 够用、不用 100T"降级为"35T 大概率够，但以太网+时序膨胀是真实破板风险，必须先跑 OOC 综合验证，并保留 100T 后备决策点"。**

**一句话：估算诚实，但"25%~54%、留有余量"是乐观叠加下的数字；最坏情况贴边，结论下早了。**

---

## ① 基线 / 可用率核对

### 20,800 LUT 分母——✅ 正确
- XC7A35T = **20,800 个 6 输入 LUT / 41,600 FF / 50 个 36Kb BRAM**，文档用 20,800 而非宣传的"33,280 逻辑单元"做分母，**口径正确，这点诚实，红方认可**。逻辑单元(LC)是含布线的市场口径，约束设计的是 LUT 数，文档没在这里耍滑头。

### 但"可用率"被默认成 100%——这是结论的第一个隐藏乐观
- **攻击点**：占用率 = 估算 LUT / 20,800，分母用了**物理总量**，等于假设"20,800 个 LUT 能 100% 用满"。**真实 FPGA 做不到。**
- **依据/反算**：
  - 布线拥塞、时钟区域(clock region)边界、IO bank 就近约束、IDELAYCTRL/ISERDES 对采样逻辑的布局锁定，都会让**有效可用 LUT 低于物理总量**。业界经验：**LUT 占用超 ~75–85% 后，布线时间暴涨、时序急剧恶化，实际工程很少把 7 系塞过 ~80%**。
  - 用 **80% 可用率**折算，有效可用 LUT ≈ **16,640**。
  - 用这个分母重算主方案 B 上沿（11,280 LUT）：**11,280 / 16,640 ≈ 68%**（而非文档的 54%）。坏情况 C 上沿（13,000）：**13,000 / 16,640 ≈ 78%**——已逼近"不该再塞"的红线。
- **裁定**：文档所有占用率应**乘 1/0.8 ≈ 1.25 的现实修正系数**来看。"留有余量"在 80% 可用率口径下大幅缩水。**文档未提可用率折算，是一处该补而未补的乐观。**

## ② 以太网估算专项质疑（MAC / UDP / buffer 逐块核）

这是 LUT 大头、最不确定、且 ORBTrace 从未验证过的部分。三块逐一核，**结论：三块都偏乐观，且相互之间漏了胶水/对接逻辑。**

### MAC（1,200~2,500 LUT）——区间下沿偏乐观，且漏了 RGMII 的时钟基础设施
- verilog-ethernet 的 `eth_mac_1g_rgmii` **核心 MAC 逻辑**落在这个区间是合理的（该核确实较精简）。但：
  - **RGMII 收发要 IDELAY/ODELAY + IODELAYCTRL + 时钟前向(ODDR/clock forwarding)**——这些虽多为 IO 原语，但其 **MMCM/时钟管理、RX 时钟域恢复、跨域同步**有 fabric 成本，文档把它塞进"0~2 BRAM"一笔带过，**LUT/FF 侧未单列**。
  - **同一颗 IDELAYCTRL 既要服务 trace 采样（200MHz ref）又要服务 RGMII**——两套 IDELAY 用户共享/复制控制器，可能要**两个 IDELAYCTRL 或额外约束**，这块没算。
  - **裁定**：MAC 取下沿 1,200 偏乐观，现实中位更接近 **1,800~2,500 + RGMII 时钟胶水数百 LUT/FF**。

### UDP/IP+ARP（1,500~3,000 LUT）——区间本身合理，但"最小集"假设偏乐观
- UDP 比 TCP 轻，区间方向对。但"含 ARP/ICMP 最小集"在**真实跑通**时往往还需要：
  - **TX 应用层到 UDP 的打包/长度/校验和拼接**、**RX 的过滤/分发**、**速率匹配 FIFO 与反压**——verilog-ethernet 的 `udp_complete` 系列把 eth_axis、ip_complete、udp、arp 全连起来后，**实测常落在 3,000~4,500 LUT**（含各级 AXIS FIFO），**上沿 3,000 偏低**。
  - **裁定**：UDP 栈完整连通后，**上沿应放到 ~4,000~4,500**，文档的 3,000 是"裸 UDP 核"而非"能跑通的栈"。

### buffer "强制转 BRAM 就解决"——⚠️ 这是被当成稳赢的最大乐观点
- **攻击点**：文档引 LiteEth 实测（双缓冲 +2,700 LUT，~1,700 为分布式RAM），然后说"对策：强制 buffer 用 BRAM，可把 1,700 LUT 转走"。**把"转走"当成总能成立的稳赢——不成立。**
- **依据**：
  1. **分布式 RAM 不是工具任性，而是有原因的**：浅而宽、需要**异步读/单周期读/多读口**的小 buffer，BRAM 推断不划算或时序不满足时，工具/IP **故意**用 LUT-RAM。RGMII RX 跨时钟域的弹性 buffer、AXIS 的 skid buffer、小深度 FWFT FIFO，**经常必须是分布式 RAM**——强行塞 BRAM 要么综合属性不被采纳，要么**牺牲时序/增加延迟**。
  2. **"转去 BRAM"与 ④ BRAM 瓶颈直接冲突**（见④）：把 1,700 LUT 的 buffer 转成 BRAM，**BRAM 占用上升**，而 trace 缓冲 + COBS FIFO + 网络 buffer 已在抢 BRAM。**它不是"消失"，是"换一个更紧的资源池"。**
  3. LiteEth 那 2,700 LUT 里**还有 ~1,000 不是分布式RAM**（是逻辑），**这 1,000 转不走**。
- **裁定**：buffer 这块，文档"转走 1,700 LUT"是**乐观假设**。现实是：部分能转（代价是 BRAM 变紧），部分转不走。**这是本表最该打问号、却被写成"对策已就绪"的地方。**

### 以太网漏项：trace 数据流 → UDP 净荷的对接逻辑
- trace 出来的是 OrbFlow/COBS 字节流，要喂进 UDP 发送，中间需要**分包、长度封装、节流、跨到 MAC 时钟域的 FIFO、以及"何时凑够一包发出"的策略逻辑**。这块在"入口小计"和"出口小计"之间**没有单列**，是个 200~600 LUT 的隐藏胶水层。

## ③ 最坏情况反算（上沿叠加 + 80% 可用率折算）

红方按要求算一次"所有模块取区间上沿 + 现实修正"的最坏情况：

| 块 | 文档上沿 LUT | 红方修正后上沿 | 修正理由 |
|----|-------------|---------------|---------|
| 入口（trace 核心） | 3,780 | 3,780 | 认可，trace 核心估得实在 |
| MAC | 2,500 | 2,500 + 400(RGMII时钟胶水) = 2,900 | ②MAC 漏时钟基础设施 |
| UDP/IP/ARP | 3,000 | 4,500 | ②"能跑通的栈"而非裸核 |
| buffer 逻辑（转不走的部分） | （文档假设 0，已转BRAM） | +1,000 | ②~1,000 非RAM逻辑转不走 |
| trace→UDP 对接胶水 | （未列） | +600 | ②漏项 |
| 杂项 | 1,000 | 1,000 | 认可 |
| **功能面积合计** | **~11,280** | **~13,780** | |
| **+ 时序收敛膨胀（见④，按 +15%）** | — | **~15,850** | 满速采样插管线/复制/物理优化 |

- **按物理 20,800 分母**：15,850 / 20,800 ≈ **76%**。
- **按 80% 可用率（16,640）分母**：15,850 / 16,640 ≈ **95%**。
- **结论**：最坏情况**逼近 95% 可用 LUT，实际上等于"塞不下/布线时序崩"**。文档的"坏情况 63%"是只在"buffer 全转走 + 不算时序膨胀 + 100% 可用率"三重乐观同时成立时才有的数字。
- **注**：这是上沿叠加的悲观值，**期望值（中位）更可能落在 50–65% 可用 LUT**——所以不是"必破"，而是"**最坏情况会破，余量没有文档说的那么足**"。结论从"留有余量"应改为"中位够用、上沿贴边"。

## ④ 时序收敛对面积的影响（被"只评面积"免责回避）

- **攻击点**：文档反复"本表只评面积不评时序"。这个免责对"时序本身"是诚实的，**但被用来回避一个面积问题：为达成时序，面积会膨胀**。纯功能面积 ≠ 实现后面积。
- **依据**：
  - **满速源同步采样**（这条路的命门）为了 setup/hold 收敛，常要：**输入管线寄存器、lane 间 deskew 寄存器复制、控制信号高扇出复制(register duplication)、物理约束导致的逻辑重排**——这些都吃 FF 和 LUT。
  - **千兆 RGMII @125MHz** 与 **trace 满速域** 两个高速时钟域，跨域路径要插同步级/FIFO，物理优化(phys_opt)阶段会**复制驱动、插 LUT1 buffer**。
  - 经验：高速设计**实现后 LUT 比综合后(功能)面积膨胀 ~10–20%**，FF 膨胀更明显（寄存器复制）。
- **裁定**：文档的"功能面积"系统性**低估实现后面积约 10–20%**。③ 已按 +15% 计入。**"只评面积"不该等于"只评功能面积"——实现后面积才是会不会破板的那个数。**

## 致命 / 严重 / 次要清单

### 致命
- **F1〔buffer"转去 BRAM"被当稳赢〕**：这是 LUT 最大不确定项，文档把"对策"写成已就绪，实则部分转不走(~1,000 LUT 逻辑)、能转的也只是把压力挪给本就紧张的 BRAM(④冲突)。**这一项直接决定 ② 出口估算可信度。**
- **F2〔最坏情况贴边/破板被"63%"掩盖〕**：上沿叠加+80%可用率+时序膨胀后达 ~95% 可用 LUT。文档"坏情况 63%"是三重乐观同时成立的产物，**给了"35T 宽裕"的错误信心**。

### 严重
- **S1〔可用率未折算〕**：分母用 100% 物理 LUT，所有占用率应×1.25 来看；54%→68%，余量大幅缩水。
- **S2〔UDP 栈上沿偏低〕**：3,000 是裸核，能跑通的 udp_complete 栈实测常 3,000~4,500，上沿应上调。
- **S3〔BRAM 可能先于 LUT 成为瓶颈〕**：见下，文档主攻 LUT，但 BRAM 在"buffer 转 BRAM"对策下会顶上来。

### 次要
- **m1〔MAC 漏 RGMII 时钟胶水〕**：数百 LUT/FF + 可能的第二个 IDELAYCTRL。
- **m2〔trace→UDP 对接胶水未单列〕**：200~600 LUT 隐藏层。
- **m3〔FF 预算未被审视〕**：41,600 FF 通常比 LUT 宽松，但寄存器复制(时序)下应顺带核一眼，文档没给 FF 占用率结论。

---

## BRAM 是否先于 LUT 成为瓶颈（专项）

- 文档 B 配置 BRAM 估 **9~18 / 50 块（18%~36%）**，看似宽松。但叠加以下后会变紧：
  - trace 主缓冲（若在 PL 侧留较大 FIFO 抗 PC 收流抖动）：连续流虽不需大缓冲，但**留几十~上百 KB 抗网络抖动是合理的**，按几块~十几块 BRAM。
  - COBS 2×256B FIFO（2 块）+ AsyncFIFO（1~2 块）+ UDP TX/RX buffer（2~4 块）。
  - **F1 的"buffer 转 BRAM"对策**：再 +2~4 块。
- **裁定**：BRAM 中位仍够（50 块不算少），但**"LUT 紧时把 buffer 赶进 BRAM"这条退路会同时推高 BRAM**——两个资源池**不能同时当对方的泄压阀**。若 LUT 和 BRAM 同时上沿，**BRAM 有可能先到 ~70%**，需一起盯。BRAM 不是首要瓶颈，但**是 F1 对策的隐藏代价**，必须连带评估。

---

## 结论裁决

### 35T 是否够？
**中位够用（期望落在 50–65% 可用 LUT），但不是文档说的"宽裕留余量"——最坏情况（以太网偏重+buffer转不走+时序膨胀+80%可用率）会贴到 ~95% 可用 LUT，存在真实破板风险。** 结论应从 §3 的"35T 够用、留有余量、不用 100T"**降级为**："35T 大概率够，以太网出口是唯一可能破板的变量，上板前必须用 OOC 综合证伪最坏情况。"

### 要不要 100T 后备？
- **不必现在就买 100T**，但**必须保留 100T 作为决策点**：
  - ¥375 省钱赌 35T，**赌的是"以太网+时序膨胀不超预期"**。若赌输，代价是**重新买板(100T 同系列引脚兼容则改约束即可，不兼容则重画约束/PCB 适配)+ 时间**，远大于 ¥375 板差价。
  - **理性做法**：先跑下面的 OOC 综合（零硬件成本），用真实数字决定。**若以太网 OOC 实测 + trace 核心 OOC 实测之和（含实现后膨胀）< ~60% 可用 LUT → 锁 35T；若 > ~70% → 直接上 100T，别赌。**

### 上板综合前必须先跑哪个 OOC 综合（按优先级）
1. **以太网栈 OOC（最高优先级）**：选定核（verilog-ethernet `udp_complete_1g_rgmii` 或 LiteEth），跑 **OOC 综合+实现**，拿到 MAC+UDP+ARP+buffer 的**实现后** LUT/FF/BRAM，并**显式查 LUT-as-RAM 数量**、确认 buffer 能否在不破坏时序的前提下转 BRAM。**这一块是 F1/F2/S2 的命门，单独跑、用实现后数字替换 ② 全部估算。**
2. **trace 采样前端 + deskew OOC**：把采样前端 + deskew 校准 + traceIF + CDC FIFO 跑 OOC 实现，验证 ① 的 deskew 500~1,500 区间，并看**时序约束下的面积膨胀**（验证 ④）。
3. **两者合并 + 时序约束的实现**：把 1+2 合到目标器件、加真实时钟约束(125MHz RGMII + 200MHz IDELAYCTRL + trace 满速域)跑实现，拿到**全设计实现后 utilization + 时序余量**——这才是"35T 是否够"的唯一权威答案。

**一句话裁决**：**方法论诚实，但结论建立在"buffer 转 BRAM 稳赢 + 100% 可用率 + 只算功能面积"三重乐观上；把这三项现实化后，35T 从"宽裕"变成"中位够、上沿贴边"。别凭这张表锁定 35T——先跑以太网栈的 OOC 综合（零成本），用实现后数字决定 35T 还是 100T，这比赌 ¥375 板差价划算得多。**
