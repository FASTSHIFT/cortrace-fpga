## 总确认

**确认可按方案丙推进：从仿真+P0/P1 零硬件起步、暂不买板、最终只买一块 Artix-7+FT601。这个结论与红方第六轮一致，落地结构正确。**

复盘整体如实，三个关键论点（Zynq DDR3 缓冲类别错误、iCESugar profiling 无时间数据、双轨 A 轨非必需）**均被准确记录，无淡化曲解**。但发现**一处事实性错误（traceIF_tb.v 端口名与现模块不符，S3 不能直接跑）**、**两处需补强的边界声明**、以及**四项应在买板前用零成本消化、但 §5 计划遗漏的风险**。逐项如下。

### 需纠正/补记的两处（不影响结论，但应回填）

- **纠正-1（归因）**：§2 Zynq 条目记了 R3（DDR3 类别错误）与"PS 仅搬运丧失理由"，但**漏记了 R2（A9 软件解析 5-15 cycle/byte 严重乐观、双核因 COBS/TPIU 串行帧依赖拿不到 2×）**。Zynq 已死，此项不影响结论，但若复盘要作为"决策档案"，应补一句，以免未来有人重提"Zynq PS 解析"时重蹈乐观。
- **纠正-2（漏记致命）**：iCESugar V1（第四轮）的致命 F3——"**满速+转接板这个真命门被推到第二版 = 重犯 Zynq'最大风险后移'老毛病**"——在 §2 未单列。它部分被 §0"低速对满速零证明力"吸收，但作为**结构性教训**（命门必须前移、单独立 PoC、不靠低速背书）值得显式保留，因为它直接约束方案丙的上板阶段排期。

## ② 型号选择裁决：Alchitry Au V2（XC7A35T-2FTG256I）+ Ft

**裁定：合理，确认可选；但有三点必须在下单前落实，且国内可得性需正视。**

- **逻辑量充足、不浪费**：trace 通路（采样前端 + traceIF + TPIU + COBS + OrbFlow + FIFO + FT601 桥）量级 ~2-4K LUT；XC7A35T 的 ~20,800 LUT / 33K 逻辑单元**绰绰有余**，无需上 100T。**注意**：此处不要重犯第二轮 R1 的"估算当事实"——真实占用以 Vivado 实现后报告为准，但**结论方向（35T 够用）成立**，因为这条路**没有 AXI-DMA/SmartConnect**（那是 Zynq 吃 LUT 的大头），比 Zynq 通路更省。
- **ISERDES/IDELAY 确认可用**：Artix-7 全系含 **ISERDESE2 + IDELAYE2 + IDELAYCTRL**（7 Series SelectIO），35T 包含，-2 速度等级对 trace 满速采样有利。✅ 物理前提成立。
- **下单前必须落实的三点（零成本，datasheet/约束文件即可查）**：
  1. **TRACECLK 落点**：选定板子 SODIMM/Br 接口上，用作 TRACECLK 的引脚必须是**时钟能力脚（MRCC/SRCC）**，才能驱动 BUFIO/BUFR→ISERDES。这是第二轮 S3 / 第五轮 S2 的老约束，**对 Artix 同样适用，且必须在买板前查 FTG256 pinout + 板子约束文件确认**。
  2. **5 线同 bank + 3.3V**：TRACED0-3 + TRACECLK 尽量同一 IO bank、bank 电压可配 3.3V（或加电平转换）。
  3. **IDELAYCTRL 的 200MHz 参考时钟**：确认板载时钟能经 MMCM 生成稳定 200MHz（IDELAY 校准的硬性前提）。
- **国内可得性提醒**：Alchitry（SparkFun）国内采购可能有渠道/周期/价格问题。**Au+Ft 的真正价值是板对板连接器替你把 FT600 的 ~40 根高速并行线走好**（第四~六轮反复强调的坑）。若改用"国内 Artix-7 板 + 外接 FT601 模块"，**这 40 根高速线的连接问题会重新出现**——届时必须选带 FMC/高速对插连接器的板，**不可用长杜邦/排针接 FT601**。这是选 Alchitry 而非"任意国产 Artix 板"的**决定性理由**，应在文档写明，避免为省钱换板后踩高速接线坑。

## ③ 仿真边界与 corner case 补充要求

### 边界声明核对
§3.2 的边界声明（✅ 验证帧组装/TPIU/COBS/OrbFlow/SWO 逻辑正确性；❌ 不验证满速时序/相位/SI）**准确、诚实，红方认可**。

### 发现的事实性错误（必须修正后才能宣称 S3 可跑）
- **traceIF_tb.v 端口名与现模块不一致**：testbench 例化用的是 `.PkAvail(...)`、`.Packet(...)`，而当前 `verilog/traceIF.v` 的输出端口是 **`FrAvail`、`Frame`**。**该 testbench 对当前模块不能直接编译通过**，§5 的 S3"装 iverilog 跑 traceIF_tb.v"不是"开箱即跑"，需先修端口名。
- **stimfiles 与该 testbench 未联动**：`stimfiles/`（`slowitm.dat`/`fastitm.dat`，`convert.py` 注明源自真实 CSV 采集）确实存在，但 `traceIF_tb.v` 用的是**硬编码 `sendByte` 序列**，并未 `$readmem` 这些 stim 文件。文档"`traceIF_tb.v` + stimfiles（真实激励）"的表述**把两件未联动的东西说成一体**，属轻微夸大。要用真实激励需自己改 testbench 读取 .dat。
- **`pytest tests/test_tpiu.py` → 3 passed 属实**：test_packetizer / test_packetizer_slow_timeout / test_demux 三个，`test_demux` 内嵌真实 ITM "hello world" 位级 golden，确为真实数据比对。✅ 这部分如实。

### 仿真层"真正通过"必须补的 corner case（Q-4 扩展）
当前 `test_demux` 只覆盖了 demux 主路径。逻辑层判通过，至少补：
1. **三种总线宽度** width=1/2/4 全测（testbench 有 WIDTH 参数但单次只跑一种，需三种都跑）。
2. **RE-sync 与 FE-sync 两条路径**（`isREsync` 分支）+ **流中途丢同步再重同步**。
3. **half-sync 序列 `0xff7f`** 处理与 `0x7fff` "pass word" 跳过（TPIUSync/traceIF 的特判分支）。
4. **背压**：output.ready 拉低时全流水线是否正确 stall、不丢字节。
5. **跨时钟域 AsyncFIFO（trace 域 → sys 域）双时钟仿真**——**这是当前所有单元测试都没覆盖的集成风险**，必须单独写双时钟 testbench（零成本），因为它是真板上最易出隐性丢字节/亚稳态的地方。

### 关键提醒（防止"仿真绿=方案可行"误读）
**这些仿真验证的是 `tpiu.py`/COBS/OrbFlow 的芯片无关解码逻辑——而上 Artix 真正要重写的是采样前端（ISERDES/IDELAY/校准），它恰恰不在这些测试覆盖范围内。** 即：仿真全绿 = "可复用的解码逻辑已确认正确"，**不等于** "Artix 采样链路已减险"。这正是第五/六轮 F2/F3 的点，请在文档显式写一句，避免团队把"仿真通过"读成"接近可用"。

## ④ 能力边界对需求方的告知是否充分

**基本充分、诚实，但需再钉死一句。**

- §0/§6.3 已诚实承认："默认产出控制流/路径占比；**耗时(性能)分析与 UAF 依赖满速+时间戳/缓冲，属上板后能力**"。无"控制流冒充性能分析"的残留措辞。✅
- **必须补钉的一句**：**仿真+P0/P1 这个起步阶段，对两个立项初衷（定位 UAF、定位性能问题）的直接产出 = 0**，它们**全部**依赖上板满速版。请明确告知需求方，避免"起步顺利"被误解为"接近交付目标"。
- **一个对需求方有利、应当写明的正向事实**：Artix+FT601 的**实时连续流**恰好**化解了第四轮 F1 的"抓快照触发+环形缓冲冲掉 UAF 根因"难题**——连续流到 PC（PC 存储近乎无限），不需要在小缓冲里"抓住崩溃瞬间"。**前提是 FT601 持续吞吐 ≥ trace 峰值、且 PC 端能持续落盘/收流。** 这是 Artix 实时路线相对 iCESugar 抓快照的实质优势，值得正面记录（也再次印证放弃抓快照是对的）。
- **耗时分析的带宽前提要先算**：一旦为"性能问题"开时间戳/周期包，带宽会显著上升。**在承诺"上板后能做耗时分析"前，必须先算最坏带宽 vs FT601 ~200MB/s 上限**（这是 N1 的连锁，目前文档只说"B 轨验证带宽"，应给一个量化的预估）。

## ⑤ 行动计划（§5）增补

§5 从仿真起步、P0/P1 并行、全绿再买板——顺序合理。补以下**应在买板前用零成本消化**的项：

1. **S0（新增，置于 S3 前）**：修 `traceIF_tb.v` 端口名（PkAvail/Packet → FrAvail/Frame），使其能对当前 traceIF.v 编译，再跑 iverilog。
2. **S3.5（新增）**：写**双时钟 AsyncFIFO（trace→sys）CDC 仿真**——当前测试盲区，零成本，必做。
3. **S5 扩展**：P0 实测 ETM 峰值率时，**顺带确认所用 STM32F429 板（Disco/Nucleo/自制）实际把 PE2-PE6 引到可接的排针**（第一轮 m1：F429 大概率不被 SDRAM 占用，但具体板子要核对）。
4. **买板前置门（新增，零成本 datasheet 核查）**：把 ②裁定里的三点（TRACECLK 落 MRCC、5 线同 bank/3.3V、200MHz 参考钟）作为**下单前必须查过的清单**，任一不满足就换板/换接口方案。
5. **S6 扩展**：PC 端不仅验"已知样本喂 Orbuculum"，还要验**Orbuculum 能从"流/设备源"实时 ingest OrbFlow**（不止读文件），确认实时链路的上位机侧命令行与版本——这是 Artix 实时路线真正要用的入口。

## ⑥ 终审结论与上板前最后 checklist

**终审结论：确认可按方案丙推进。** 复盘如实、型号合理、从仿真起步的决策正确且第一步（tpiu 仿真）已实跑验证。本终审不再提出致命/严重质疑——剩余项都是"零成本可在买板前消化"的补强，不构成阻断。

**上板（买 Artix）前的最后 checklist（全绿才下单）：**

- [ ] **仿真层**：traceIF_tb 端口修正后 iverilog 跑通；`pytest` 全绿；补测 width 1/2/4、RE/FE-sync、丢同步重同步、背压、**trace→sys CDC 双时钟仿真** —— 全过（Q-4 扩展）。
- [ ] **P0**：STM32F429 配通 ETM(仅程序流)+TPIU 4-bit，示波器确认 5 线波形稳定；**实测程序流峰值率**（满速档 FT601 选型的 gating 数）。
- [ ] **P1/上位机**：已知 OrbFlow 样本喂 Orbuculum 位级解出函数跳转；**确认 Orbuculum 实时流/设备源 ingest 路径**可用。
- [ ] **选板 datasheet 门**：TRACECLK 落 MRCC/SRCC、5 线同 bank 可配 3.3V、板载可生成 200MHz IDELAYCTRL 参考钟 —— 三项书面确认。
- [ ] **出口连接**：确认 FT601 走**板对板/FMC 高速连接器**（Alchitry Ft 或等价），**不靠长排针接 40 根高速线**。
- [ ] **带宽账**：若需"耗时分析"，先算开时间戳包后的最坏带宽 vs FT601 ~200MB/s，确认不超。
- [ ] **需求方对齐**：书面告知——起步阶段对 UAF/性能两个初衷产出为 0，二者属上板满速版能力；满速源同步采样+转接板 SI 是命门，**单独立 PoC、用眼图/时序硬阈值（眼高≥0.5UI、setup/hold≥0.3ns）判收，不靠低速结果背书**。

**一句话终审**：**复盘诚实、结论正确、起点已验证；把上面那处 testbench 端口错误修掉、把 CDC 仿真和选板 datasheet 三项零成本前置补进计划，方案丙即可放心推进——记住唯一不变的命门仍是上板后的满速源同步采样+信号完整性，它必须单独立 PoC，仿真绿和 P0/P1 绿都不为它背书。**
