## 1. 修正方法论：同一 .bin、运行时切 cache（红方优先级 1）

把 cache 开关从**编译期宏**改成**运行时标志**，彻底消除"两个二进制"：
- flag 字放 **RAM_D1 `0x24000000`**（CubeMX 把 .data/.bss 放 DTCMRAM，C 启动**从不碰**
  RAM_D1，flag 从 openocd 写入活到 main）。
- openocd 在 ETM cfg 的 `reset halt` 之后写 flag，结尾 `resume`（无再次复位）→ 固件读 flag
  决定 `SCB_EnableI/DCache()`。
- **两次运行烧同一个 .bin、用同一个 ELF 解码**，唯一差异 = openocd 写的一个 word。

**验证单变量成立**：
```
md5 /tmp/rtoff/mem.bin == /tmp/rton/mem.bin  = 8920afd0...（完全相同）✓
CCR: flag=0 -> 0x00040200 (I/D cache OFF) ; flag=0xCACE -> 0x00070200 (I/D cache ON) ✓
```
cache 确实被开关了（CCR bit16/17），且解码镜像逐字节相同——**真单变量**。

## 2. 决定性结果：真单变量下 cache 的影响消失

### 2.1 CoreMark 分数：完全相同（cache 未提速）
| flag | cache | Iterations/Sec |
|---|---|---|
| 0 | OFF（CCR=0x40200）| **203.861629** |
| 0xCACE | ON（CCR=0x70200）| **203.864302** |

**同一二进制下开/关 cache，CoreMark 分数一模一样**（差 0.001%）。这颗 H743 在 50M/
FLASH_LATENCY_2、CoreMark 工作集下 cache 增益≈0（代码/数据基本已零等待）。
> 注：这也解释了原 proposal 37 的"2.8× 数据 / 305 vs 203 分数"差异——**那大部分来自两个
> 不同二进制，不是 cache**。红方"单变量破产污染结论"命中。

### 2.2 执行路径：一致（cache 不改架构执行，回答用户真正的问题 (ii)）
同一起点对比一次 OFF vs ON 的执行 PC 集合：
```
OFF 执行 43 个 PC，ON 执行 87 个 PC
OFF 独有（ON 没走到）= 1 个，且是 core_state_transition（CoreMark 真函数，抓样点不同）
=> OFF 的 42/43 个 PC 全被 ON 包含；ON 是 OFF 的近似超集（同路径、抓样窗口覆盖更多迭代）
```
**没有出现"cache ON 走进了不同/错误函数"——执行了哪些指令 (ii) 不变。** 这正面回答用户问题：
**cache 对架构执行透明，不改执行路径**（符合 ARMv7-M 架构保证）。

### 2.3 SysTick 异常：抽签，非 cache 作用（证伪原证据 B）
各抓 3 次 BB=1：
```
OFF EXCEPTION: {0, 0, 0}
ON  EXCEPTION: {2, 0, 0}   <- 只有 1/3 次出现，另 2 次为 0
```
**ON 的异常出现是偶发（1/3），不是稳定现象**。546µs 窗口 vs 1ms SysTick 周期，期望每窗口
跨过 ~0.5 次 tick——正是"有时抓到、有时抓不到"的抽签。**红方 Q2 成立：原证据 B 把窗口相位
抽签误当"cache 改数据"，撤回。**

### 2.4 deframed 净字节：ON 系统性偏高，但属 (i) 层面
```
OFF deframed: {4492, 3530, 4512}  均值 ~4178
ON  deframed: {9911, 11933, 8059} 均值 ~9968  (~2.4×)
```
**分数相同（执行相同）但 ON 的 trace 字节 ~2.4×**。这不是执行了更多指令（2.2 证路径一致、
2.1 证速度相同），而是 **cache 开启改变了取指/数据访问的时序模式**，使同一 546µs 窗口内
trace FIFO 的排空节奏、HSYNC 填充比例、地址包 vs atom 的打包密度不同。
**这是 (i) 层面（trace 流的时间展开/打包），不是 (ii)（执行路径）。** 诚实归类：属"时序经由
打包密度"的效应，仍是速度/时序族，不是"cache 往 trace 注入了新的数据机制"。

## 3. 裁决（回应红方 r30）

| 红方质疑 | 本轮实测裁决 |
|------|------|
| 单变量破产（两个二进制）| **接受**，重做为同一 .bin 运行时切 cache（mem.bin MD5 相同）|
| 证据 B SysTick = 抽签 | **接受**，3 次重测 ON={2,0,0} 证实偶发抽签，撤回 B |
| 证据 C 拿手册冒充实测 | **接受**，Cancel/微架构异常实测 0/0，撤回 C |
| (i) vs (ii) 偷换概念 | **接受**，新实验证 (ii) 执行路径一致，cache 对架构执行透明 |
| 总结论"cache 改数据本质" | **证伪**，撤回 |

**修正后的诚实结论**：
1. **cache 对程序架构执行透明**——同一二进制下开/关 cache，CoreMark 分数相同、执行 PC 集合
   一致（超集关系=抓样点差异）。**用户问题 (ii) 的答案：cache 不改执行路径、不改执行了哪些
   指令。**
2. cache 在本平台本负载**连速度都没改**（50M/低等待下增益≈0），所以"cache 全速拉稀锚点"这个
   在 150M 观察到的现象，**根因是频率（150M vs 50M）本身**，不是 cache——**这进一步修正了
   proposal 36/r29 里"cache 拉大锚点间距"的表述：真正拉大锚点间距的是高主频（指令率），cache
   只是高主频得以全速的使能条件之一，本实验的 50M 下 cache 增益为 0 故看不出差异**。
3. trace 字节率 (i) 层面 ON 偏高，是 cache 改变访存时序→FIFO 打包密度的效应，非执行内容变化。

## 5. 对主线的意义

- proposal 37 原结论撤回，但**不影响 r29 的假调用根因**（atom 盲推漂移仍成立，那是 BB=0 +
  高主频稀疏锚点的解码局限）。
- 修正认知：**拉稀锚点的是高主频（指令吞吐率），不是 cache 本身**。cache 是"让高主频得以全速"
  的使能条件，但在增益为 0 的低频点，开关 cache 对 trace 无实质影响。
- "满血 + 精确 BB=0 函数级不可达"的结论**不变**（满血=高主频→锚点稀→盲推漂移；带宽峰值超端口），
  只是把"cache"从直接推手更正为"高主频"这个真正的自变量。
