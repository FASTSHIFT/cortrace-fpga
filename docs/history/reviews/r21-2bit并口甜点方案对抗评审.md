# r21 · 提案 19「2-bit 并口 trace 甜点」对抗性评审

> 评审对象：`proposals/19-2bit并口trace甜点方案.md`
> 立场：红方，严格证伪。盯死"实测 vs 外推"的边界。
> 历史模式：本作者多次被抓到"用推断冒充实测""乐观措辞掩盖工作量"——逐条按此戒备。

---

## 总裁决（先给）

**改 + 强降级。这不是"甜点"，是一个建立在两层未验证假设（满速编码密度可外推 + DDR）之上、且回避了一个更便宜的硬约束（F429 并口 TRACECLK 实际上限）的中间档。** 它的真问题不在算术，而在**北极星错了**：作者用大量实测数字（91196B、1.48Mbit/s、89% P-header）营造"实测锚定"的可信感，但**这些实测全部来自 stall 模式紧密循环的 proj_add**，而提案的核心卖点"不开 stall 跑满速调用栈"恰恰是这些实测**完全没覆盖**的场景。**实测数字是真的，但它们锚定的不是提案要论证的命题。** 这是比"用推断冒充实测"更隐蔽的一招——**用真实测,锚错命题**。

**最致命的自拆台**：提案 §6 自己列出"峰值 169 > 2-bit SDR@50M 的 100，若超仍需开轻 stall"。**而"不开 stall"是这个甜点区别于 SWO 的唯一卖点**——如果满速峰值仍要开 stall，那 2-bit 相对 SWO 的本质优势（不拖慢 CPU）就没了，只剩"带宽大一点的、仍要 stall 的、多一套要维护的"中间档。

## 逐条质疑

### Q1 带宽地基：1.12 bit/指令 能从 stall 紧密循环外推到满速真实代码吗？

【**证伪**】

一句话：**编码密度 1.12 bit/指令是 proj_add 紧密循环 + stall 模式的实测，外推到 LVGL 满速是把特例当通例，且方向性错误。**

依据：
1. **紧密循环是 P-header 编码的最优案例,不是代表案例**。proj_add 的 `add; loop_sum` 紧循环——绝大多数指令是直线 + 高度可预测分支,P-header 的 atom 压缩率最高(一条 Format-1 P-header 能塞十几个 atom)。**LVGL 那种调用密集代码:深调用栈、大量间接分支(函数指针/vtable)、return**——而**间接分支地址包(br_out=0 下仍发)是 32-bit 地址,比 atom 贵一个量级**。提案自己的实测就写明:间接分支占 10% 包数但"字节/间接分支=96",**意味着 950 个间接分支吃掉了约 950×? 的字节,在调用密集代码里这个比例会暴涨**。
2. **方向性错误**:作者在 §4.1 注释里写"实际 CPI>1、大量直线用 P-header 极省编码,真实均值落在保守~中之间"——**这是往低了猜**。但调用密集代码恰恰相反:间接分支比例上升→地址包占比上升→**编码密度比紧密循环更高(更贵)**,真实满速码率可能**高于** 169 的"峰值",不是落在保守~中。**作者把对自己有利的方向当成了"实际通常"。**
3. **stall vs 满速的 atom 分布未必同分布**:stall 模式下 CPU 走走停停,trace FIFO 不溢出,atom 流是"完整记录";满速不开 stall 时若 FIFO 瞬时满,ETM 会插 overflow packet——**这本身改变码率构成**,而提案的 1.48Mbit/s 是 stall 下测的,没有 overflow,**不能代表满速**。

**最低成本证伪**:不需要 2-bit 硬件。**换固件**——用 LVGL(或任何调用密集真实负载)在**现有 SWO 链路**上抓一段,跑 etm_pkt_census,看编码密度(bit/指令)和间接分支字节占比 vs proj_add 差多少。**若 LVGL 的 bit/指令 显著 > 1.12(比如 2-3×)→ 满速码率外推全错,2-bit 余量蒸发。成本:换个固件抓一次,0 新硬件。** 这一刀直接证伪 §4 的地基。

### Q2 SDR/DDR 敞口：核心卖点是不是建在未验证的 DDR 假设上？

【**证伪**(卖点依赖未验证假设)】

依据:
1. 提案 §4.2 自己承认 SDR/DDR 未定、带宽差 2×,且 §4.3 的"留有余量"结论用的是 **"@50MHz SDR 100 / DDR 200"** 这个区间。但看清楚:
   - **SDR @ 50MHz = 100 Mbit/s**,而满速码率保守 90、中 135、峰值 169。**SDR 下只覆盖到"保守",中和峰值都超**。
   - **只有 DDR @ 50MHz = 200** 才真正"留有余量"。
   - **所以"留有余量"这个卖点,成立与否完全取决于 DDR 假设。** 提案嘴上说"必须 PoC 实测",但 §7 结论又直接写"对满速调用栈留余量"——**把未验证的 DDR 当成了既定结论来下结**。
2. **CoreSight TPIU 的 TRACEDATA 实际是 SDR,不是 DDR**。这是提案最该被打的事实错误倾向:ARM TPIU 并口的 TRACECLK 与 TRACEDATA 关系——**TRACEDATA 在 TRACECLK 双沿都有效(DDR)是 CoreSight 标准行为**,这点提案蒙对了方向(§4.2 注"通常 DDR")。但"通常"不等于"F429 实测",而 F429 的 TPIU 是不是按 DDR 输出、我们 IDDR 能不能在该 TRACECLK 收敛——**全未验**。提案把"CoreSight 通常 DDR"这个一般性陈述,当成了"F429 一定 DDR 所以余量在"的具体保证。

**最低成本证伪**:这个不需要 2-bit 全链路,**示波器/LA 抓 F429 在并口模式下的 TRACECLK + TRACEDATA,看数据是在单沿还是双沿翻转**。成本:配一次 TPIU 并口模式 + 一次 LA 抓取。**若是 SDR → @50MHz 只有 100,中/峰值满速超,"不开 stall 跑满速"证伪,退回开 stall(那就没有相对 SWO 的本质优势)。**

### Q3 F429 到底能不能 2-bit + 多高 TRACECLK？

【**存疑→倾向证伪**(频率假设无依据)】

依据:
1. 提案把 TRACECLK **25/50/75MHz** 当可选项列进带宽表,但**没有一个数字有 F429 datasheet 或实测支撑**。这是典型的"凑频率让带宽表好看":要 200Mbit/s 余量,就需要 50MHz DDR,于是 50MHz 就出现在表里——**先有想要的结论,再填频率**。
2. **F429 并口 trace 的实际 TRACECLK 上限没查**。TRACECLK 来自 HCLK 经 TPIU 分频(类似 SWO 的 ACPR,但并口路径),最高能到多少受:① TPIU 并口时钟树 ② **GPIO Fmax(r18 已确立:50pF 负载下 GPIO Fmax 仅 50MHz,且那是引脚翻转极限不是眼图)**。
3. **r18 的教训直接适用**:并口 TRACECLK 50-75MHz 在杜邦线/板上 SI 下,眼图大概率开不到——而 r16 已实测**并口 trace 重启就崩到 15% unknown**(那还是更低速)。**50-75MHz 并口在我们这套连接下是纸面值。**
4. 更要命:**提案自己在 §0 说"4-bit 的 nARMED 长线命门" 2-bit 没有,但 2-bit 仍是源同步并口,TRACECLK 越高越紧(§6 自己承认)**——所以 2-bit 把"4 条数据线 skew"减半了,但**没有解决"TRACECLK 高速下 SI"这个并口的真命门**。而带宽余量恰恰需要高 TRACECLK。**自相矛盾:要余量就要高 TRACECLK,而高 TRACECLK 正是 SI 命门所在。**

**最低成本证伪**:查 F429 datasheet 的 I/O AC characteristics(trace 脚的 Fmax)+ 算 TPIU 并口分频能给的 TRACECLK 实际点。**若 50MHz 在 datasheet/SI 上不现实 → 带宽表的 50/75MHz 行作废,只剩 25MHz(SDR 50/DDR 100),连"中"满速都覆盖不了。成本:查手册,0 硬件。**

### Q4 "甜点"的必要性：它解决了哪个"不做就过不去"的问题？

【**证伪**(非必要踏脚石)】

依据:
1. 提案自己定位:SWO 已打通(基线)、4-bit 是 stage5 终态。2-bit 夹在中间。**问一句:不做 2-bit,从 SWO 直接攻 4-bit,过不去吗?** 提案没有论证"4-bit 必须经过 2-bit 这个踏脚石"——它说 2-bit"为 4-bit 积累源同步采样经验",但**源同步 IDDR 采样经验 SWO 支线(IDDR 400MSa/s)已经积累了**(提案 §4.2 自己引用)。2-bit 在采样架构上**不比 SWO 多教任何新东西**(都是 IDDR 采样),只是多了 1 条数据线 + 真 TRACECLK 源同步——而那 1 条线和真时钟,**要学也是直接在 4-bit 上学**(4-bit 的 SI 难点是它特有的,2-bit 学不到)。
2. **维护成本**:2-bit 要一套独立的 traceIF 变体(2-bit 输入裁剪)+ 一轮 PoC + 一套判收。提案说"复用 4-bit traceIF 裁成 2-bit",但 4-bit traceIF 现在**还没在板上跑通**(stage5 命门未解),"裁剪一个还没跑通的东西"不是复用,是再开一个分支。
3. **它解决的唯一独有问题**是"比 SWO 带宽高 + 不开 stall"——而 Q1/Q2/Q3 已证这个"不开 stall"建立在三层未验证假设(编码密度可外推 + DDR + 50MHz 可达)上,**任一不成立,2-bit 就退化成"仍要 stall、SI 比 SWO 难、带宽没本质优势"的中间档**。

**裁决**:2-bit 不是"不做过不去"的踏脚石。要么直接攻 4-bit(终态),要么用 SWO(已通)。**2-bit 是徒增一条要维护的路径。**

### Q5 P-header 砍不掉，是否动摇用户根本诉求？

【**成立**(提案这条是诚实的,但结论指向"不该做 2-bit")】

依据:
1. **这是提案全文最诚实的一段**(§2):ETM-M4 0 地址比较器、br_out=0 已是下限、P-header 占 89% 砍不掉、"只抓 BL/BLX/POP"硬件做不到。**这条实测扎实(sidetrack §14 逐寄存器验证),红方认可,不挑。**
2. **但这条恰恰反过来削弱 2-bit 的理由**。用户的原始动机是"低带宽下拿调用栈"。既然 P-header 砍不掉(89%),那"调用栈"的真实带宽需求就是接近满速 ETM 码率——**这正是 SWO 扛不住、要开 stall 的原因**。2-bit 想"不开 stall"装下它,又依赖未验证的 DDR/50MHz(Q2/Q3)。
3. **提案一句带过的 DWT PC 采样才是对用户诉求更直接的路**:用户要"调用栈/热点",DWT 周期采 PC + 中断**带宽极低(KB/s 级)、不需要满速通道、不需要 stall、SI 用 SWO 单线就够**。它不是完整指令流,但**"调用栈/profiling"恰恰不需要完整指令流**。提案把 DWT"一句带过",而它可能是比 2-bit 更省、更对诉求的方案——**这是被过早排除的假设**。

**裁决**:P-header 砍不掉这条诚实,但它的逻辑后果是"低带宽拿调用栈"在完整指令流路线上做不到,**应该认真评估 DWT PC 采样(低带宽 + SWO 单线),而不是用 2-bit 硬扩管子**。

### Q6 GPIO/外设冲突

【**存疑**(又一个被轻描淡写的硬约束)】

依据:
1. 提案 §5 写 "GPIO 配 TRACECLK + TRACED0/D1(**PE2/PE3/PE4 一类**,需查 F429 trace 复用脚)"——**连用哪几个脚都还是"一类""需查",说明没核**。
2. 历史模式:r12/r16 的并口 trace 用的就是 PE2-6,**现在的固件/板子这些脚有没有被占用、和 SWO 支线(PB3)是否共存、和 RGMII/其他外设是否冲突,提案没查**。"需确认不冲突"是把硬约束推给未来。
3. 这条单独不致命(查手册能解),但它是**"乐观措辞掩盖工作量"的又一个实例**:把"必须逐脚核对 + 可能要改板/改固件管脚分配"压缩成一句"需确认"。

**最低成本**:查 F429 datasheet trace AF 表 + 比对现固件/板子 PE2/3/4 占用。0 硬件。

## 总裁决：改 + 强降级(倾向砍)

**这个"甜点"是甜在纸面上的。** 它的三层地基——① 满速编码密度可从 stall 紧密循环外推 ② TRACEDATA 是 DDR ③ TRACECLK 能上 50MHz——**全部未验证,且任一不成立,2-bit 就退化成"仍要 stall、SI 比 SWO 难、带宽无本质优势、多一套要维护"的鸡肋中间档**。而提案 §6 自己已经承认峰值会超、"仍需开轻 stall"——**等于自己拆了"不开 stall"这个唯一卖点**。

**正确动作**:
1. **先做 Q1 的零硬件证伪**(下一节),它一刀打掉地基。
2. 同时认真评估 **Q5 的 DWT PC 采样**——若用户真正诉求是"调用栈/热点"而非完整指令流,DWT + SWO 单线可能比 2-bit 更省更对路,**直接让 2-bit 这个中间档没必要**。
3. 战略上:Stage5 命门是 4-bit 满速 SI(r16 还崩着)。2-bit 既不解决它(高 TRACECLK SI 命门照在),又不是它的必要踏脚石。**精力应回 4-bit 命门或 DWT,不是新开 2-bit 分支。**

---

## 最低成本"一票证伪"实验

**换固件,不碰硬件:在现有 SWO 链路上抓一段 LVGL(或任何调用密集真实负载)的 ETM,跑 etm_pkt_census,量它的编码密度(bit/指令)和间接分支字节占比,与 proj_add 的 1.12 比。**

- **若 LVGL 编码密度显著 > 1.12(预期 2-3×,因间接分支/调用密集)** → §4 满速码率外推全错,真实满速码率远超 169,2-bit @任何现实 TRACECLK 都扛不住"不开 stall",**整个甜点论证一票否决**。
- 成本:0 新硬件、0 新 RTL,换个固件抓一次现有 SWO。
- **这一刀同时验证 Q1(外推)和 Q5(P-header 占比在真实代码下更高)**,是性价比最高的证伪。

附加(若上面没直接否掉):**示波器看 F429 并口 TRACECLK 单沿/双沿(Q2 的 SDR/DDR)** + **查 datasheet trace 脚 Fmax(Q3)** —— 两个都 0 硬件成本,共同决定带宽表是不是空中楼阁。

## 点破

**你这次没有用"推断冒充实测"——你用了真实测(91196B/1.48Mbit/s/89% P-header,全是真的),但锚错了命题。** 那些数字全部来自 **stall 模式 + proj_add 紧密循环**,而你要论证的是 **"不开 stall + 满速 + 真实代码"**——这是实测**完全没覆盖**的场景。用真实测营造"实测锚定"的可信感,再把结论悄悄延伸到实测不及之处,**比纯推断更难被发现,但本质一样是越界外推**。最硬的破绽你自己写在 §6 了:峰值 169 > SDR@50M 的 100,"仍需开轻 stall"——**你亲手承认了甜点的核心卖点(不开 stall)可能不成立。** 当一个方案的唯一独有优势,被作者自己在风险表里标了"可能不成立",那它就不是甜点,是个需要先证伪地基的假设。先换 LVGL 固件抓一次,让真实代码的编码密度告诉你 169 这个数是不是早就低估了。
